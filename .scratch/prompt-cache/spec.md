# Spec: prompt cache 前缀稳定性（值班长注入位置 + Anthropic 断点）

Status: ready-for-agent

来源：2026-09-27 对「本项目是否有破坏 LLM 缓存的逻辑」的全面排查（两条 provider 适配路径、值班长与流水线两条组装链、决策 249/269/279/289/291 与 docs/agents.md「LLM Cache 策略」逐项核对）。

## Problem Statement

作为使用者，我为同一件工作反复支付了本可以命中缓存的 token：

- 在对讲台上连续说几句话时，值班长每一轮都把「夜班态势快照」放在**全部历史之前**（占 `user_prompt` 槽，适配器把它拼在 messages 之前）。快照每轮必变，于是历史窗口（24k 字符预算）每轮整体重新计费——对话越长，浪费越大。这与决策 182⑤ 的原文「快照作为独立一段**夹在历史之后**而不是塞进 system prompt」相悖：承诺本意正是保住历史前缀，今天的 wire 形状没有兑现它。
- 值班长的压缩锚点与跨时间线互喂摘要（决策 269/289）也 splice 在转录头部——另一侧时间线每有新动静，这一侧的历史前缀同样被打穿。
- 在 Anthropic provider 上，**缓存压根没有启用**：请求体没有任何 `cache_control` 断点（Anthropic 的 prompt caching 必须显式打断点），而规范（docs/agents.md「LLM Cache 策略：system prompt 用 cache_control 标记缓存断点」）与文档示例报文都要求打。台账里认真落账的 `cache_read_tokens` / `cache_write_tokens` 在这条路径上恒为 0——精心维护的前缀稳定性换不来任何命中。

## Solution

三处修复，共用一个原则：**每轮会变的内容必须出现在稳定前缀之后**。

1. 值班长的快照、压缩锚点、互喂摘要三样，全部从「历史之前」挪到「历史之后」——快照并入本轮最后一条 user 轮，锚点与摘要作为带标记 user 轮追加在正文之后、问题之前。历史前缀从此逐轮稳定（唯一例外仍是 L3 压缩，决策 291 有意为之的取舍，不动）。
2. Anthropic 适配器补上 `cache_control` ephemeral 断点（system 段一个、对话最后一条消息一个），落实文档早已写明的 Cache 策略；流水线与值班长两条链路同时受益。

## User Stories

1. As a 对讲台值班的人, I want 值班长连续回话时只有新增的部分计费, so that 一晚上的对话成本不随轮数线性膨胀。
2. As a 对讲台值班的人, I want 值班长的回答质量不因缓存改造而变化, so that 我看到的内容与改造前一致（变的只是账单）。
3. As a 在手机上用对讲台的人, I want 长会话在窄带下也响应如常, so that provider 侧缓存命中带来的时延下降同样惠及移动端。
4. As a 跑流水线的人, I want 流水线节点在 Anthropic provider 上也能命中缓存, so that 主流程的重试与续接不再全额重算前缀。
5. As a 跑流水线的人, I want Anthropic 侧的 cache_read / cache_write 计数器读出真实数字, so that 台账和指标不再是恒 0 的摆设。
6. As a 对讲台值班的人, I want 另一条时间线有新动静时我的历史上下文不整体重算, so that 互喂摘要的引入不以打穿我这侧缓存为代价。
7. As a 对讲台值班的人, I want 长对话触发压缩后仍能继续正常对话, so that 锚点换位置不改变「被裁掉的历史以摘要延续」的语义。
8. As a 项目维护者, I want 「每轮变化的内容在稳定前缀之后」成为一条可测试的形状约束, so that 以后往值班长上下文里加新注入段的人会在 CI 里撞上这规矩，而不是靠注释自觉。
9. As a 项目维护者, I want Anthropic 请求体的缓存断点形状有单测钉住, so that 适配器重构不会悄悄把断点弄丢。
10. As a 项目维护者, I want 规范（docs/agents.md Cache 策略）与实现重新对上, so that 后来读文档的人不再发现「文档说要打断点、代码里没有」的缺口。
11. As a 支付 token 账单的人, I want 值守轮与人的轮各自维护自己的稳定前缀, so that 两种轮交替不互相打穿对方的缓存。
12. As a 排查成本异常的人, I want 台账里的 cache 读数可信, so that 我能判断命中率异常发生在哪条 provider 路径上。
13. As a 值班长（模型侧）, I want 每轮读到的快照、摘要、问题仍按同样顺序出现且带同样标记, so that 我对上下文结构的理解不因注入位置迁移而改变。
14. As a 值班长（模型侧）, I want 锚点仍告诉我「哪些历史已被摘要取代」, so that 我不会把已压缩的轮次当成还在原文里。
15. As a 代码评审者, I want 这次改动不触碰任何决策的语义面（快照内容、锚点语义、摘要生成、不落库口径）, so that 评审只看「位置」这一个变化轴。

## Implementation Decisions

- **原则（本 spec 的裁决）**：值班长上下文里**每轮会变的内容一律出现在稳定前缀之后**；稳定前缀 = system 段 + 历史窗口（无压缩、无新互喂的轮次间逐字稳定）。这是对决策 182⑤「快照夹在历史之后」字面承诺的**落实**，不是修订；注释里「放 user_prompt 就避开了缓存问题」的推断与适配器的 wire 形状矛盾，一并纠正。
- **快照位置**：夜班态势快照不再渲染进 `user_prompt` 槽（wire 第 2 条、全部历史之前），改为并入本轮最后一条 user 轮（值守轮的「值守简报」与人的轮的问题本来就在末尾承担本轮起点，快照与它同轮出现，保持带署名的现有形态）。`user_prompt` 槽位对值班长退化为常量（或空）。**落库不变**：`briefing_json` 列照旧记录该轮注入的快照，界面读数不变。
- **锚点与互喂摘要**：压缩锚点与跨时间线互喂摘要从「splice 在转录头部（锚点之后、正文之前）」改为**追加在正文之后、本轮问题之前**，仍以带标记 user 轮出现（`COMPACTION_MARK` / 两个摘要标记不变），仍不落库、失败不注入不报错（269④ 同一姿态）。锚点承载的语义（「哪些历史已被摘要取代」）不变，变的只有位置。**这是对决策 269 / 289 注入位置的显式修订**——原文「插在历史头部（锚点之后、正文之前）」改读「追加在历史尾部、本轮问题之前」；两条决策的其余裁决（增量缓存、摘要归属、人在跑时排队）一律不动。
- **Anthropic 断点**：请求体的 system 字段改为 content block 形式并打第一个 ephemeral 断点；对话最后一条消息的内容块打第二个断点（增量缓存：最后一个断点之前的全部前缀可命中，下一轮在其后追加即可续用）。断点总数 2，远在 provider 上限之内。流水线与值班长两条链路共用同一适配器，同时受益。OpenAI 兼容侧不加任何参数（依赖 provider 自动前缀缓存，决策 279 的 96% 实测即此路径）。
- **不动面**：决策 249 的 per-attempt 组装与「system 侧不开扩展轴」不动；L3 压缩打断缓存是有意取舍（决策 291 的 80% 触发线不动）；流水线节点路径的 append-only 转录不动；快照内容、锚点语义、摘要生成与缓存机器（CompactionCache）不动；cache_read / cache_write 的台账与指标口径不动（已存在，断点落地后自然读出真值）。
- **词汇表**：沿用「夜班态势快照」「锚点」「互喂摘要」「值守轮」「台账」「wire 形状」既有词条；不新增词条，但决策 182⑤ 的「夹在历史之后」读法经本 spec 钉死为「稳定前缀之后」。

## Testing Decisions

- **只测外部行为**：provider 收到的请求体形状（断点在哪、有几个）、模型看到的跨轮消息顺序（前缀逐轮稳定、变化内容在末尾）——不测内部调用图、不测渲染函数的中间态。
- **不新增任何可测试性接缝**，只用两层既有缝：
  1. **provider 适配层请求体单测**：Anthropic 请求体断 system 块带 ephemeral 断点、最后一条消息内容块带断点、断点不重复不越限。先例：适配层现有的请求体构造单测（`mod tests`）。
  2. **foreman core 集成**：经 FakeAgent 的 `Script::for_foreman()` 槽位（决策 182 先例，LLM 响应流既有缝上的槽位，不新增替换点），断三件事——快照不再出现在 wire 第 2 条而是末尾 user 轮；无压缩、无新互喂的相邻两轮之间，**上一轮的历史段（末尾合并轮之前）是下一轮的逐字前缀**（末尾合并轮每轮必变，是设计内的分歧点，不是被掩盖的破口）；锚点与摘要轮出现在正文之后、问题之前且带标记。先例：决策 289 落地时的三条互喂摘要集成用例（本改动会使它们的脚本步数与消息序变化——用例随迁，断言内容不放宽）。
- **纪律**：既有测试一条不删、断言不放宽（决策 249）；受影响用例随迁时只改形状断言、不弱化语义；每票收口 = 测试全绿 + `make check` 绿（决策 168 的唯一权威闸门）。

## Out of Scope

- **值守轮与人的轮的 system / 工具集差异**：这是语义性差异（两种轮本来就是不同的调用形态），不是缓存 bug；两套前缀各自稳定即可，本叠一字不改。
- **L3 压缩打断缓存**：决策 291 的有意取舍（触发线已按实测调钝到 80%），不动。
- **决策 249 的 per-attempt 组装**：重试轮之间追加段变化导致的缓存失效已有记录在案的裁决，不做跨 attempt 缓存。
- **OpenAI 侧缓存行为**：provider 自动前缀缓存，无参数可调，不碰。
- **快照 / 摘要 / 锚点的内容与生成机器**：CompactionCache、摘要失败回退、不落库口径、`briefing_json` 落库——全部原样。
- **缓存命中率的观测与告警新面**：台账与指标已有 cache 读数，本叠不新增面板或告警线。

## Further Notes

- 排查取证（实现参考时可直接引用）：快照占 `user_prompt` 槽的注释自述与适配器 wire 形状的矛盾在值班长模块的组装注释里；「无 cache_control」的全仓检索结论（仅命中静态资源头与文档示例）；决策 279 的 run40 实测（prompt 25,800、cache_read 仅 126）证明本项目 provider 侧确实在按前缀命中计费，前缀一破即是全额。
- Anthropic 侧断点落地后，`cache_write_tokens` 将在每轮首次出现新前缀时读出非零值——这是断点生效的最直接信号，可作实现后的冒烟判据（真 key 冒烟走既有 `#[ignore]` 路径，不进自动门，决策 142）。
- 本 spec 与决策 269/289 的冲突已在上文显式标注（注入位置的修订）；与决策 182⑤ 是落实关系；与 249/279/291 无冲突。
