# 对讲台内置操作流水线的出厂技能（foreman-operate-pipeline）

**Status:** done（决策 261，票 01–04 已落地）

> 来源：用户诉求「为对讲台内置一个操作 AgentPipeline 的 skill」，经 grilling 13 轮拷问

## Problem Statement

对讲台里坐着值班长，它已经握着 21 件工具——`task` 一族能建任务、挪阶段、审闸门，读数一族
能查台账，本服务写操作全部走「提议 + 值班经理按键」的确认闸。**硬件都齐了，缺的是操作手册**：

- **指令到动作没有稳定的翻译层。** 值班经理在对讲台里说「把 X 推进一步」「这三张卡挨个重试」，
  值班长只能靠模型自由发挥去猜该调哪个工具、带什么参数、先读什么再提议。猜得对不对全凭运气，
  没有一份沉淀了规则的文本告诉它：先读 `allowed_actions`、pending 的原因要用原文、同一张任务的
  连锁动作要分步提、批量要逐票排队。
- **不可逆动作的确认纪律没有成文载体。** 「提议 + 按键」的闸是代码里的事实（D 层恒提议），
  但「哪些话术该翻译成提议、哪些只该读数回答、批量时怎么排队」这套操作语义没有任何地方写着。
- **知识没有出厂形态。** 技能系统要求技能是技能根下的真 SKILL.md 文件，可预览、可信任、可升级；
  但产品不携带任何技能正文（决策 172①），首启技能根是空的——「内置」今天没有落地形态，
  装完应用后值班长对「怎么操作流水线」一无所知。

## Solution

给对讲台内置一份**出厂技能 `operate-pipeline`**——一份纯文本操作手册，教值班长把值班经理的
自然语言翻译成既有工具的正确调用：

1. **真技能文件，出厂即在。** 手册是技能根下的真 SKILL.md（走既有技能系统），正文随产品携带，
   启动时幂等种入技能根：只补缺失、不覆盖用户改过的、被删下次启动补回；卸载端点对白名单技能
   拒绝——出厂技能不可删。
2. **每轮点名，在线拉取。** foreman 阶段配置行的 `persona_append` 默认播种一句点名（「遇操作类
   指令先按名拉 `operate-pipeline`」），每一轮都出现在值班长的 system prompt 里；正文不注入，
   值班长用现成的 `Skill` 工具按需拉取——历史窗口不被手册挤占，改手册下一轮即生效。
3. **只翻译，不绕闸。** 手册教的是「读数用哪个工具、写操作提什么提议、批量怎么排队」；一切写
   操作仍走既有「提议 + 值班经理按键」，不新增任何改状态的代码路径。
4. **值守轮同样生效。** 点名在 prompt 里，值守轮自动轮同样按手册来：发现卡点备好提议，值班经理
   醒来批量按键。

## User Stories

1. 作为值班经理，我想在对讲台用自然语言问「X 任务到哪一步了」并得到基于台账读数的回答，这样我不必去kanban 页面翻。
2. 作为值班经理，我想说「把 X 推进一步」后收到一张参数正确的提议卡，这样我按键就能执行、不必自己去任务详情找按钮。
3. 作为值班经理，我想让 merge / cancel / retry 这类不可逆动作每一张都由我逐次按键确认，这样错误指令不会直接改坏状态。
4. 作为值班经理，我想让「读」类问题（卡在哪、为什么停）只产生回答、不产生提议，这样读写分层清晰、屏上不堆废卡。
5. 作为值班经理，我想让值班长引用 `allowed_actions` 与 pending 原因**原文**作答，这样它的话有出处而不是转述枚举名。
6. 作为值班经理，我想下令「这三张任务挨个重试」时值班长逐票各提一张提议、排好顺序给我，这样批量也是一票一确认。
7. 作为值班经理，我想让同一张任务的连锁动作分步提议（等第一张落地再提第二张），这样第二张不会被态势漂移拒掉。
8. 作为值班经理，我想让提议过期（TTL 10 分钟）后值班长能重新提议，这样我按得慢不会永久卡死。
9. 作为值班经理，我想让值守轮发现卡点时也按手册备好提议，这样我睡醒直接按键处置，而不是醒来再从头下令。
10. 作为值班经理，我想让值守轮的提议同样准确、同样走按键确认，这样自动轮不因为省事而绕闸。
11. 作为值班长，我想每一轮都看到那句点名，这样操作类指令不会靠运气才触发手册。
12. 作为值班长，我想按需拉取手册正文而不是每轮全文注入，这样历史窗口不被手册挤占（决策 182 的既有立场）。
13. 作为值班长，我想在手册里看到批量、TTL、同任务分步这些坑的明确规则，这样我不必每次现推现错。
14. 作为值班长，我想在手册里看到范围声明（只操作看板任务、不碰 `.scratch` 票），这样两套状态体系不被我搅在一起。
15. 作为安装用户，我想装完应用技能根里就有 `operate-pipeline`，这样出厂能力不依赖我手动导入或配置市场。
16. 作为安装用户，我想出厂技能删不掉（卸载被拒且报文说清），这样内置能力不会被一次误点抹掉。
17. 作为安装用户，我想我改过的手册内容不被启动播种覆盖，这样我的本地定制保留。
18. 作为安装用户，我想即使有人从磁盘上删了手册文件，下次启动也会补回，这样系统回到出厂一致状态。
19. 作为设置页用户，我想在阶段配置里看见、编辑、关闭那句点名，这样注入是配置层行为而不是藏在代码里的硬编码。
20. 作为设置页用户，我想手册出现在技能列表里并可预览，这样它就是技能系统的普通一员（除了一条不可删）。
21. 作为开发者，我想手册是真 SKILL.md 走既有技能系统，这样信任、预览、按名拉取的机制全部沿用、不另起炉灶。
22. 作为开发者，我想决策 172① 的窄口修订有编号、有留痕，这样未来读决策日志知道出厂技能白名单的边界在哪。
23. 作为开发者，我想提议参数与按钮直发的参数逐字一致，这样按键执行走的是同一道端点校验、没有第二条路。
24. 作为测试者，我想三件结构断言可自动化回归（点名在场 / 真拉了正文 / 提议参数同源），这样核心链路坏了机器先知道。
25. 作为测试者，我想一份手工黄金剧本（几句真实自然语言的期望提议序列）写进票面，这样「测试全绿但手册教得很蠢」有人兜底。
26. 作为值班经理，我想对讲台的界面形状不因本特性改变（不加新按钮、不加新面板），这样我肌肉记忆不动。

## Implementation Decisions

### 出厂技能与决策 172① 的窄口修订

1. **技能名 `operate-pipeline`，形态是技能根下的真 SKILL.md**（frontmatter 带 description；
   不设 `disable_model_invocation`）。它经值班长现成的 `Skill` 工具按名拉取，不走 prompt 全文注入。
2. **正文随产品携带、启动幂等种入技能根**——这是对**决策 172① 的窄口修订**：新决策开「出厂
   技能白名单」（首期仅 `operate-pipeline` 一条），边界为：正文只此一份白名单内、启动时**只补
   缺失**（文件在则一字不动——用户改过不覆盖、用户从磁盘删了下次启动补回）、白名单常量即边界
   的唯一事实源。172①「二进制不夹带技能正文挤兑技能根」的本意不被推翻。
3. **卸载端点对白名单技能拒绝**，报文说清「出厂技能不可删除」；普通技能的卸载行为不变。
   磁盘层的补种是防御性的（API 已经删不掉，补种兜住手工删文件）。
4. **不在 foreman 阶段配置行的 `skills_json` 里声明该技能。** 理由：声明会让启动校验 fail fast——
   手工删掉文件后整个产品起不来，代价不对称；不声明时 `Skill` 工具对不存在的名字返回友好提示，
   悬空点名无害。技能列表（`read_skills` / 设置页）仍照常列出它，因为它就在技能根里。

### 点名注入

5. **点名住 foreman 阶段配置行的 `persona_append`，默认播种一句**（大意：「涉及流水线操作的指令，
   先用 Skill 工具按名拉取 `operate-pipeline` 手册，按手册执行」）。拼装位置在人格段之后、
   工具纪律段之前，每轮（含值守轮）都在场。种的是**点名一句话**，不是技能正文——不撞 172①。
6. **播种的是配置默认值**：首次无该配置时写入；用户改过/清空过则尊重用户值（设置页可见、可编辑、
   可关）。这不是每轮注入技能正文——那条路（决策 182「值班长 prompt 不注入技能」）保持不变，
   本 spec 只加一行指针。

### 手册内容纲要（正文写进票面拆分）

7. **读流程**：态势问题先用 `read_board` / `read_task` 取真读数；pending 任务必须引用原因原文；
   回答引数据不编造；不产生提议。
8. **写流程**：`task` 族七动作（create / resume / retry / cancel / review / merge / unstick）各自的
   适用条件与参数来源（动作必须来自该任务此刻的 `allowed_actions`）；一切写操作产出提议、
   永不绕过按键（D 层恒提议是代码事实，手册复述为纪律）。
9. **批量规则（Q11）**：逐票一卡、每任务至多一张在途卡、跨任务排队给人逐张按；同任务连锁动作
   等第一张落地、看到回执再提下一张（单任务态势指纹会拒第二张）；TTL 过期重新提议；**不做
   一键批量端点**。
10. **值守轮规则（Q10）**：值守轮同样按手册来——发现卡点先读数定因、备好提议，等人按键；
    守住值守轮自身的节流与工具摘除纪律。
11. **范围声明（Q6）**：只操作看板任务（init→done 的 DB 流水线本体）；`.scratch` markdown 票
    不在范围内、手册明说不碰。

### 零新代码路径

12. **不新增 task 动作**（split / archive / model-override / stewardship 等缺件等真实需求再议，
    Q5）；**不新增任何改状态的端点或第二条执行实现**——提议执行照旧直接调配对端点的处理器。
13. **对讲台 UI 零改动**：提议卡、按键、状态区形状全部沿用（既有 e2e 断言「回话里没有按钮」
    等继续成立）。

### 文档同步

14. **决策日志**：新增窄口修订决策（编号落表时取，≥261）并在决策 172① 行追加修订标注；
    与 176 / 182 / 204 / 207 / 247（对讲台、提议、工具清单）的既有裁决无冲突，引用即可。
15. **术语表**：新增「出厂技能」词条（白名单、幂等种入、不可删三要素）；`docs/testing.md`
    决策↔测试映射表补行。

## Testing Decisions

**好测试的标准（沿用本仓口径）**：只测外部行为，不测实现细节；不测 prompt 的**效果**（手册教得
好不好），只测**组装与链路**（点名在不在、拉没拉、参数对不对）——效果由黄金剧本人工兜底。

**接缝：零新增，全部骑在既有缝上**（本仓可测试性接缝是权威表，决策 143；本批与 UX 审计、
决策 251 批次同一姿态）：

| 落点 | 既有接缝 | 测什么 |
|---|---|---|
| 主缝：core 值班长集成测试 | LLM 响应流接缝的 `Script::for_foreman()` 槽位（决策 182⑧）；工具层全部真实执行 | **Q12 三件**：① 点名段每轮在场（取证取模型真正收到的 system prompt，照既有纪律段测试的姿态），值守轮再钉一条；② 脚本让模型发 `Skill(name=operate-pipeline)`，断言回执是手册正文；③ 拉完正文产出的 `task` 提议 args 与配对端点按钮直发的参数逐字一致 |
| 播种语义 | `AGENTPIPELINE_HOME` 环境变量缝 + `TestHome`（决策 143 既有五缝之一） | 空 home 启动后技能根有该文件；改过不覆盖；删过下次启动补回；连启两次幂等 |
| API 契约 | L3 tower oneshot 契约测试（`api_contract.rs` 先例） | `DELETE /skills/operate-pipeline` 拒绝且报文说清出厂技能不可删；对照组删普通技能照旧成功；`persona_append` 默认值的写入与回读走阶段配置端点 |
| 人工验收 | 真 LLM 冒烟同姿态（`#[ignore`]、不进默认门） | **Q12(b) 手工黄金剧本**：几句真实自然语言指令（「把 X 推进一步」「这三张挨个重试」「review 里那张怎么样了」）走一遍，人肉确认提议序列与回答质量；剧本逐条写进对应票面当验收项 |

**明确不测**：播种逻辑不开新 trait/替换点（启动路径纯逻辑，`TestHome` 独立 home 天然隔离）；
不加新 e2e spec（对讲台 UI 形状不变，既有 `talk.spec.ts` 断言继续覆盖 UI 侧）；不测手册正文的
措辞质量进自动门。

**先例**：主缝取证照 `tests/foreman.rs` 的纪律段与工具集断言；提议参数同源照 `api_contract.rs`
「按下之后真的落盘 / 参数过不了校验提议不消耗」的既有性质；卸载契约照技能导入卸载组用例；
黄金剧本照真 LLM 冒烟的 opt-in 姿态。

## Out of Scope

- **`.scratch` markdown 票的操作通道**（Q6：零通道现状保持，两套状态体系不搅混；需要时另立议题）。
- **新增 `task` 动作**（split / archive / model-override / stewardship，Q5）。
- **一键批量执行端点**（Q11：批量走逐票提议，零新代码）。
- **值班长 prompt 全文注入手册正文**（决策 182 立场不变；只有点名指针）。
- **foreman 行 `skills_json` 声明**（避免手工删文件后启动 fail fast，见决策 4）。
- **黄金剧本的自动化**、**新增 e2e spec**（人工验收项，不进默认质量门）。
- **经技能市场分发该技能**（出厂白名单即来源，不做市场条目）。
- **对讲台 UI 的任何形状改动**。
- **prompt 效果离线 eval、性能负载、非 Chromium 浏览器**（沿用本仓既有测试边界）。

## Further Notes

- **13 条裁决与 grilling 轮次对应**：Q1 人下令 agent 执行 / Q2 读+无损写 / Q3 默认单票 /
  Q4 逐次按键（复用既有提议闸）/ Q5 纯手册零新代码 / Q6 只管 DB 任务 / Q7 真文件+显式点名 /
  Q8 窄口修订 172① / Q9 persona_append 播种 / Q10 值守轮同效 / Q11 逐票一卡批量 /
  Q12 三断言+黄金剧本 / Q13 不允许删除（API 拒 + 磁盘删了启动补回）。
- **核心风险是手册质量而非链路**：链路有三件自动化兜着；手册教得蠢不蠢只有黄金剧本能发现——
  剧本不是可选项，是本 spec 验收的一半。
- **勘察钉住的关键事实**（实现票可直接引用）：值班长 system prompt 组装不注入技能（决策 182
  立场，doc 注释明文）；`Skill` 工具必须先知名字、`read_skills` 不含正文；提议态势指纹是
  **单任务级**（status/stage/node/allowed_actions），跨任务批量互不干扰、同任务第二张必被拒；
  多条 pending 提议共存是被测试钉住的常态、无唯一性约束；值守轮广告集仍含 `task`（只摘
  `read_conversation` / `run_command`）；首启播种无先例（决策 172① 退场注释），本 spec 是第一条。
- **实现拆票建议**（供 to-tickets 参考，非裁决）：① 决策落表 + 手册正文撰写；② 播种与白名单
  不可删 + 契约测试；③ persona_append 默认点名 + 主缝三件断言；④ 黄金剧本入票 + 文档同步。
