# 01: 结构化选项提问——值班长抛 2–4 个选项等人点选

**What to build:**（先裁决、后动手——撞车点见文末）对标 ZCode AskUserQuestion：值班长在需要
人做选择时抛出 2–4 个**可点的选项**（外加自由文本口），人选一个回给它继续。现状它只能把
选择题写成自由文本，人得打字回答——拍板类对话里这是每天都在付的摩擦。

**Blocked by:** None（拷问即可开始；裁决落 `docs/decisions.md` 后实现）

**Status:** done（2026-09-24）

**撞的裁决（这就是它进破边界叠的全部理由，决策 262②）：** 决策 176④ / 207③ 钉死
「时间线上唯一的按钮是操作台提议轮里的确认钮」。选项钮是**第二种钮**，加它即修订那两条——
所以不单独立项拷问不动手。它**不是**提议（选项 ≠ 打算执行的动作），所以不能简单塞进
`.turn.prop`；也不能进回复正文（「回复里永远没有按钮」是票 04 的硬要求，`talk.spec.ts`
有断言 `reply.locator('button')` count 0）。

**拷问时要裁的分支：**

- **(a) 第三种轮型 `.turn.ask`**：操作台名牌下的一轮，渲染 N 颗选项钮 + 自由文本口；
  选中即作为下一条 user 消息发回。与提议轮（执行/拒绝）平级、框色另定。
- **(b) 复用提议轮但换 payload**：提议表加 `kind: question`，选项存 args——省一轮型，
  但「提议 = 打算执行的动作」的语义被稀释，`proposals.ts` 的 expired/按不下去逻辑要跟着分叉。
- **(c) 不给钮、只给格式纪律**：人格里要求选项写成 `A/B/C` 列表，人回字母——零界面改动、
  零裁决修订，但没解决「点选」这个真摩擦，只解决排版。

**边界草案（拷问输入，不是结论）**：选项内容进得了模型上下文（它是说出口的话）；
选中结果落台账为一条 user 消息（既有写入路径，不新造表）；一轮最多一个未决问题
（两个问题人得先答哪个？）；值守轮**不许**发选项（它在叫人，不在问人——要问也该等人在场）。
