# `run_command` 的权限模式（run-command-permissions）

**状态（2026-09-17）：四张票均未开工。** 权限模式的档位字段、环境层的那道闸、值班长的命令接线、
文档与残余风险登记都还没有落地；`run_command` 对值班长仍然不可用。


裁决（决策 206）：`run_command` 与文件工具这类**环境层**能力按档位走（`auto` / `ask` / `deny`），
而**本服务的写接口恒为提议 + 确认钮**、不读档位。

**一句话规则**：能不能配，看失败代价落在哪——环境层的错误落在文件与机器里（可回滚、有日志），
状态机写动作的错误会改变流水线的事实（有依赖边、有 worktree 准入、有合入门）。**前者可配，后者不可配。**

**默认值等于现状**：真实阶段 `auto`（与今天逐字相同）、`foreman` 行 `ask`。落地不改变任何已运行行为。

**这一批修订了残余风险的接受面**：`auto` 档下值班长可经 `run_command` 读走
`data/agentpipeline.db` 里的 provider 明文密钥（决策 112），**无补偿**——`FileToolPolicy` 不管命令，
`cwd` 域对命令也几乎无约束（命令自己 `cd` 就出去了）。故决策 206 修订 19（修订）/ 104 / 179 的接受面，
把「agent 经命令读走密钥」这条从流水线扩到对讲台，并归入「等 OS 级沙箱」（`docs/operations.md:1226`
登记为正式候选，「本层所有残余风险的唯一根本解」）。这是用户知悉后接受的取舍，票 04 负责写在明处。

**依赖**：本批的票 02 依赖 `foreman-capabilities` 的 02 / 03（`ask` 档要落到那张提议表与那颗钮上），
票 03 依赖 `foreman-sessions` 01（命令日志的会话归属列）。**票 01 可以先做**（它只是加一列）。
