# 02: 推荐行标出「这是哪个仓的哪一份」

**What to build:** 推荐面板的每一行显示出这份推荐的**来源定位**（`owner/repo` + 技能目录），让「照着这个仓
的哪一份装」在点按钮之前就看得见，也让「已装的那份是不是清单这份」在界面上有据可查。

**Blocked by:** None (can start immediately)

**Status:** done（2026-09-18；实机与闸门读数见文末「实施收尾」）

- [x] 前端 `RecommendedSkill` 类型补上 `repo` / `dir`（后端已在回，两者的空值形态都要声明得到）
- [x] 行上显示来源；写法沿用技能市场已有的来源呈现，不自创第五种
- [x] 契约用例断言响应里这两个键存在（逐行钉 `owner/repo` 形态、目录非空，并钉**不下发 commit**）
- [ ] ~~覆盖「这个技能不在清单里 → 值为 null」的情形~~ ——**这一格做不到，理由就地留痕**：行的名字
      取自 `recommended_skill_names`（就是这份清单），定位又按同一个 `(阶段, 名字)` 回来，`find`
      必然命中，故后端那两个字段从本端点**不可能**是 `null`。硬造只会变成「喂端点不会产生的形态」，
      那是假的覆盖。类型与界面仍容得下 `null`（组件层有一条用例钉「不画空壳」），字段注释也写明
      了这一支是防御。
- [x] 组件用例钉住渲染（含 `repo` / `dir` 为空时不渲染空壳）
- [x] `npm run check`、vitest、`vite build` 全过

**Notes（实现提示）:**

- 后端 `/skills/recommendations` 已经在下发这两个键（决策 194 补的定位字段），是**前端类型没声明、
  界面也没人用**——契约漂移的典型：多给的字段没人接，于是「一键安装」在界面上看不出装的是哪一份。
- 显示它的理由与决策 194 的理由同源：清单的全部意义是「给还没装的人照着装」，而 GitHub 模式下
  照着装要知道哪个仓、仓里哪个目录。它同时是 01 那条「本地已装的是不是清单这份」判定的用户可见面。
- 定位字段是**指针不是名录**：不要在界面或清单里钉 commit（那会让常量随上游漂移变成陈旧数据），
  commit 仍由技能市场的列表在浏览那一刻补上。

**两处代码评审的收口**：

1. 契约用例里两个字段用 `as_str().unwrap_or_default()` 取值——那不是本仓的 fail-fast 写法（类型不对
   会被静默换成空串，报错会说成「目录不能是空的」而盖掉真因）。改成 `.expect(...)`。

   用 `filter` 兜了四种组合（其中两种不可能出现），组件用例还钉了「只有仓时只写仓」——那是把不可能
   的状态写进契约。改成「两段都在才成行」，删掉那条用例，把不变量写进类型注释。
