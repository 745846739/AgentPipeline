# 闸门失败复检期的重复上报（gate-failure-respam）

**状态（2026-10-06）：已落地（决策 388）。**

用户诉求原文（2026-10-06）：「现在频繁给我发test失败的pwa通知，大约一分钟一次，为什么」

**这批要补的差距一句话**：一次 merge 测试闸门失败（`cargo test --quiet` 600s 超时，按决策 85
踢回 test 复检）本该只打扰人一次，实际 **11 分钟推了 12+ 条内容全同的 PWA 通知**——调度器
值守轮把 `merge_result.gate == Fail` 这份**状态**当**事件**轮询，且拿 `task.updated_at` 充当
待办的 `occurred_at`；复检中的任务 `updated_at` 每次工具调用都刷新，去重键
`(task_id, kind, occurred_at)` 永不重复，于是每轮巡扫都是一条「新」待办。出机线那侧只剩
60s 推送冷却在顶（礼貌配置 `cooldown_sec=60`），正好一分钟一条。

**实证账**（106，任务 01M450DK2GKZP4PJ4FVRAFAGXZ，监控记录
`.scratch/monitor-01M450DK2GKZP4PJ4FVRAFAGXZ.md`）：

- 03:03:57Z merge 测试闸门失败 → kickback 回 test/execute（attempt 10）。
- 03:03:57Z–03:11:52Z 产生 12+ 条 `gate_failure` 待办，`detail_json` 完全相同
  （`gate_failure_kind=test`、`output=测试命令 cargo test --quiet 退出码 -1 命令超时（600s）`），
  每条数秒内即被消费（推送）。
- **决定性证据**：待办表里的 `occurred_at` 与任务详情的 `updated_at` 精确到纳秒一致
  （如 `2026-10-06T03:10:28.119700544Z`）——键取的就是 `updated_at`，而它复检期间一直在动。

**语义违反**：术语表「待办（attention）」词条写明 `occurred_at` 是事件**发生**的时刻，不是
写入时刻。闸门失败这件事发生在 kickback 那一刻，之后 `updated_at` 的每次刷新都是别的事件
（工具调用、模型请求），不是新的闸门失败。

**与既有决策的关系**：

- 决策 234 的三重节流（60s 去抖 + 同任务 30 分钟冷却 + 每小时 12 次唤醒上限）管的是
  **值守轮唤醒**；这次打穿的是**出机线推送**（决策 287 失败族照推 + 礼貌冷却）。源头
  重复记行让两条线都收到成批的同事件待办。
- 决策 271（watch-failure-quiet）修过同构的「闹钟」病，其原则「一个事件只打扰人一次」
  在**源头**保证——本票同法，不动推送侧。
- 决策 85 的 kickback 分流本身不动：闸门失败踢回复检是对的，错的只在复检期间的重复记账。

## 明确不做

- **推送侧再加同内容退避**：病根在源头重复记行，推上去再加退避是给症状打补丁；且
  「一个事件只打扰人一次」应由源头保证（决策 271 原则）。
- **merge 闸门 `cargo test` 600s 超时本身的诊断**：执行体当时正在自主排查（属该任务的
  工作面，非本仓缺陷）；超时配置是否合理另行按证据裁。
- **不动 234 / 287 的任何口径**：待办照旧唤醒、失败族照旧推送——修的是「一个事件变成
  十二条」，不是「这条不该响」。

## 决策

落地时照决策日志末节形状续写一条（占 **#388**）：gate_failure 的记行以**事件**为准——
`occurred_at` 取闸门失败落定（kickback 过渡）的时刻，复检期间不重记；闸门重新评估再次
失败才算新事件。同步校对术语表「待办」词条的措辞（`occurred_at` 语义原句已对，补的是
「状态不得充当事件」这半句的实证）。
