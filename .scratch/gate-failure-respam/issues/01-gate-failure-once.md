# 01: 闸门失败在复检期间**只记一次**

**What to build:** 从用户视角：一次闸门失败只收到**一条**「闸门失败」推送——任务被踢回
复检后无论跑多久、`updated_at` 刷新多少次，都不会再冒第二条内容全同的通知；只有当闸门
**重新评估并再次失败**（下一次 merge/develop 闸门真的又跑败了），才收到下一条。

**为什么**：调度器值守轮现在轮询的是 `merge_result.gate == Fail` 这份**状态**并拿
`task.updated_at` 充当待办的 `occurred_at`——复检中的任务每几十秒刷新一次 `updated_at`，
去重键 `(task_id, kind, occurred_at)` 永不重复，一次失败被记成十几行、逐条推送（实测
11 分钟 12+ 条，见 README 实证账）。这同时违反术语表「待办」词条的语义：`occurred_at`
是事件**发生**的时刻，不是写入时刻。

**形状**：

- `occurred_at` 改取**事件发生时刻**：闸门失败落定的那一刻（merge_result 写入 gate=Fail /
  kickback 过渡的时刻），复检期间保持不变——同一份失败的 gate=Fail 状态被再次轮询到时，
  去重键不变，落不进第二行（既有唯一索引天然兜底）。
- **闸门重新评估再次失败 = 新事件**：新的失败有自己的落定时刻，照记一行、照唤醒照推送。
  判据必须是「新的一次闸门评估失败」，不是「gate=Fail 还在」——不许把真失败吞掉。
- **唤醒面与出机线一字不动**：`gate_failure` 照旧唤醒值守（决策 234 三重节流管着）、
  失败族照旧推送（决策 287）。修的是「一个事件变成十二条」，不是「这条不该响」。
- 决策 85 的 kickback 分流不动：复检该踢还是踢。

**Blocked by:** None（可立即开工）

**Status:** done

- [x] 用例（钉原缺陷）：merge 闸门失败 → 任务回 test 复检 → 期间 `updated_at` 刷新 N 次
  （或值守轮巡扫 N 轮）→ 待办表里 `gate_failure` **只有一行**，且推送恰一次
- [x] 用例（不吞真失败）：第一次失败复检完成后闸门再次评估、再次失败 → **新增一行**，
  `occurred_at` 是第二次失败的时刻
- [x] 用例（状态清除后不再报）：复检成功、闸门通过（gate 被 Pass 覆盖）→ 值守轮巡扫
  不再记 `gate_failure`
