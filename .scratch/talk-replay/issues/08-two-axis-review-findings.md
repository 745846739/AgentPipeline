# 08: 两轴评审的残留发现（收口时未改，逐条待议）

**What to build:** 收口那轮两轴评审（Standards + Spec）在实现里读出的四条残留——三条是实现与
spec 的细缝、一条是判据在并发下的边界。收口这一轮**只把文档修了**（`design/frontend-design.md`
§12.3 补四行、`.scratch/foreman-talk/CONTRACT.md` 的签名与载荷对齐），这四条**留在这里**，
不夹带进收口提交：每一条都牵动一个产品/设计决定，不是补个判据就能收的。

**Blocked by:** talk-replay 01–07 收口（本轮已收）；其中 4 条互相独立，可各自成票

**Status:** done（已拆票，决策 363，2026-10-01）

**拆票去向：** ①→[09](09-step-landing-batch.md)、②→[10](10-e2e-gaps.md)、
③→[11](11-session-totals-status.md)、④→[12](12-parallel-lines.md)。以下四条为裁决底稿，
原文保留。

- [x] **①工具步骤的落库时机**（Spec 轴 → 票 09）：spec 决策 3 说「thinking、工具调用步骤、逐字正文
      **三者都随广播落库**」，而实现里段序 / 痕迹只在**一批工具跑完**（`settle_round`）才进
      那一行（`LiveTurn::reserve_event_pose` 只领位置号、不进现场）。于是一次长工具执行中途
      拍下的快照看不到那一步，SIGKILL 落在工具批中间时那一步整段丢——与 User Story 5 / 22
      「中断轮里保留 thinking 与工具调用步骤」有细缝。**为什么当时那样写**：转录契约要求工具
      结果紧跟发起它的 assistant 消息，工具批中间插半截段序会把一批切成两半（决策 293 的
      批后判定点同一条理由）。**待议**：是把「落库」也按批对齐并对齐措辞，还是把段序改成
      逐步刷写（要付转录契约的账）。
- [x] **②两条 e2e 缺口**（Spec 轴 / 票 02 清单 → 票 10）：`frontend/e2e/talk.spec.ts` 里没有
      「**切走再切回**」这条（票 02 checklist 点名的），也没有「**重启后中断轮带标记出现在
      时间线**」这条（Testing Decisions 的 L4 那一格）。前者靠 store 的在飞现场 + venv
      单测覆盖、后者靠 `restart_recovery.rs`（后端标状态）+ `delegation-scan`（标记单一
      来源）+ `foreman.test.ts`（中断行落 settled 支）三点覆盖，**端到端那一格空着**。
- [x] **③页头合计的读数口径**（Spec 轴 → 票 11）：`foreman_session_totals` 按 `role = assistant`
      求和，而**在途行也是 assistant 行**——于是页头「本次会话 N tok / N 次调用」在一轮
      进行中途会跟着涨（收口后不涨；失败轮丢弃后又回落）。spec 说合计口径**不动**
      （决策 204⑤）。**待议**：是把在途行排除（加 `status IS NULL`，恢复旧口径），还是
      认下「合计含进行中那一轮」这条新口径并写进决策。
- [x] **④`spliceAccepts` 在两条并发行时的边界**（Spec 轴，判据 `frontend/src/realtime/foreman.ts`
      → 票 12）：
      现判据对「`ledger_id` 与基准行对不上」的增量**放行**（走既有路径接）。一个会话里同时
      跑两条在途行是决策 7 明确允许的（值守轮 + 人的轮），此时**另一条行**的增量会被并进
      基准行那一轮渲染，与快照里那条行已有的字**可能重一遍**。spec 决策 5 写的是「只接受
      `seq > seq0` 的增量」。**为什么当时放行**：另一条行的内容归它自己那一屏的基准管，
      拿本屏的基准去丢它怕丢字。**待议**：两条并行的呈现规则本身要定（各自的基准？只渲
      当前行的尾巴？），定了再改判据与单测。
