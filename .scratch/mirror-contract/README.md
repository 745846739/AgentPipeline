# 前端手抄的镜像：删的删、钉的钉（mirror-contract）

**状态（2026-09-23）：票 01–03 待实现（`Status: ready-for-agent`）。** 本目录来自一次架构评审
（`improve-codebase-architecture`）的候选 8「前端类型面是手抄的镜像，零机器校验」，经三轮拷问
（Q1–Q6）定下范围与判据。评审报告是临时的、不入库；设计结论以本文件与决策 252–254 为准。

同一轮评审的候选 1 / 2 / 3 / 4 / 5 / 7 / 10 已由决策 245–251 落地。**本目录只处理候选 8**，
且**只处理它的「值」那一半**——「形」的那一半（`api/types.ts` 的 DTO 字段）由**决策 254 押后**，
重开条件写在决策里。

## 一、问题的真实形状

候选 8 在评审报告里的写法是「`types.ts` 是手抄镜像、零机器校验」。核完事实之后，这个写法
**不准**，真实形状是两件不同的事，命运也不同：

| | 「形」的镜像 | 「值」的镜像 |
|---|---|---|
| 是什么 | `api/types.ts` 的 102 个类型，对应响应 DTO 字段 | 枚举成员、键集、常量值的字面量副本 |
| 痛是现在的还是潜在的 | **潜在的**——19 个提交 17 个配对，零事故记录 | **现在的**——43 处字面量、一个重编码整个枚举的 switch |
| 本批 | **押后**（决策 254） | **做**（决策 252 / 253） |

「值」的镜像里又分两种处置，**判据是「前端能不能等后端」**（见词条「镜像的两把刀」）：

- **能等**（数据已经到了才判定）→ **删镜像**：让后端把那个值当字段发过来。决策 252。
- **不能等**（判定可能发生在任何 API 调用之前 / 是编译期类型）→ **钉住**：共享表，两侧同断言
  方向。决策 253。

## 二、为什么「删镜像」是本仓已经用熟的刀，不是新发明

决策 247⑤ 已经用同一把刀修过一次同类问题：`Talk.svelte` 那张 18 键手抄 `TOOL_LABELS`，缺 4 个词、
带一个死键 `delete_file`、还和 `proposalToolLabel` 的 8 个 case 打架。当时的修法是**删掉那张表、
让后端供给**（`GET /foreman/tools`），落成 `lib/toolLabels.ts` 现在的形态——它只负责取数与查表，
注释写着「后端是**唯一事实源**：`ForemanToolSpec.label` 是必填字段，加工具不写标签直接编译不过」。

票 01 是把这把刀用在另两个哨兵上，不是发明新做法。

## 三、票 01 的设计要点（两个字段而不是一个枚举）

三处哨兵的事实（都核过）：

| 哨兵 | 后端定义 | 谁在写 | 前端谁在读 | 处置 |
|---|---|---|---|---|
| `FOREMAN_WATCH_MARK` `【值守播报】` | `foreman.rs:435` | 后端拼进正文 `:1349` | `Talk.svelte:337,427` | **改字段** |
| `FOREMAN_FAILED_TURN_MARK` `【没跑起来】` | `foreman.rs:1808` | 后端拼进正文 | `realtime/foreman.ts:320,338`、`Talk.svelte:330,412` | **改字段** |
| `FOREMAN_ATTRIBUTION_MARK` `【归因】` | `foreman.rs:1834` | 后端（仅供模型输出、随后剥掉） | **无人**（生产代码零读取） | **直接删** |

**归属哨兵为什么能直接删**：`message_wire`（`app/src/routes/foreman.rs:1296-1307`）把前缀剥掉、
解析成 `attribution` / `attribution_label` / `attribution_reason` 三个字段发出来了（决策 235 / 238）。
前端那份 `FOREMAN_ATTRIBUTION_MARK`（`realtime/foreman.ts:303`）只出现在自己的定义与
`foreman.test.ts:373` 那条断言里。**那条断言是 `expect('【归因】').toBe('【归因】')`**——前端字面量
与前端字面量自比，Rust 改成 `【归因x】` 它照样绿，而标题写着「与后端同源（原样镜像）」。故常量
与测试一起删，零行为变化。

**为什么 `kind` + `proactive` 是两个字段**：它们**正交**。「自发的轮失败了」（值守轮失败）是可能的
组合，而今天它算成 `failed` 且 `proactive=false`（因为 proactive 要求 `role === 'assistant'`）——
压成一个五值枚举会让这个组合**从形状上不可能**。分开写，将来要显示「值班长自己醒来说的那一轮
失败了」时不必再动接口。

`role` 字段**保留**：存储与查询仍在用，且它是观测类字段（`storage/foreman.rs:185` 明写非法值
不打断查询）。

## 四、票 02 / 03 的分界（两张表，不是一个）

| | 成员表（票 02） | 规格表（票 03） |
|---|---|---|
| 内容 | `Stage` / `PendingKind` 的**成员** | 键的**顺序**、哪些是伪键、展示标签 |
| 谁维护 | Rust 导出，前端断言 | 手写，两侧各自断言 |
| 漂了是什么症状 | 前端认不出一个值（`FromStr` 失败 / 格子不显示） | 格子顺序不对 / 伪键掉出配置页 |
| 覆盖 | `api/types.ts:21,37` 两个联合 | `STAGE_KEYS`（`stageConfigs.ts:18-33`）、`PSEUDO_KEYS`（`:50-55`）、`TERMINAL_STATUSES`（`stewardship.ts:18`）、`pendingLabel`（`pipeline.ts:551-588`） |

**为什么成员表要 Rust 导出**：`Stage` / `PendingKind` 的成员**就是枚举本身**，手抄一遍等于把枚举
抄第二遍，而抄的那份自己还会漂。`PendingKind` 的 `as_str` / `FromStr`（`types.rs:279-323`）已经
是权威表，导出它即可。

**为什么规格表要手写**：哪些键是「不进 `Stage` 枚举的配置键」、格子按什么次序排，是**规格**——
枚举推不出来。`PSEUDO_STAGE_KEYS`（`app/src/routes/stage_configs.rs:27-32`）自己也是手写的 4 项
数组，它和前端那份的关系是「同一份规格的两个副本」，不是「一个从另一个生成」。

**强度参照本仓已有的强档**：`theme/css-parity.test.ts`（逐值双向）、`lib/talkLayout.test.ts`
（断点逐字）。**不取** `lib/behavior-map.test.ts` 那一档——它只断言引用的路径存在，值漂了拦不住。

## 五、票 01 的行为变化与它的见证

票 01 是**唯一有行为变化**的一批：消息线上形状多两个字段，前端不再解析正文。见证方式：
`api_contract.rs` 加一条断言（`kind` / `proactive` 按构造的场景取值正确，且 `content` 里**仍有**
那个哨兵前缀——前缀不删，只是不再由前端解释它），加前端 `realtime/foreman.test.ts` 里
`failed` / `proactive` 的用例改成读字段而不是造前缀字符串。

**注意**：`content` 里的哨兵**不能被删掉**。它是给模型看的（`foreman.rs:887` 的值守简报模板、
`:1349` 的播报写入），也是人翻台账时认得出「这条是系统写的」的标记。本票只改**前端怎么认**，
不改**后端写什么**。

## 六、明确不做

- **不做「形」的那一半**（`api/types.ts` DTO 字段）——决策 254 押后，重开条件见那条决策。
- **不引运行时校验**（zod / valibot / io-ts）——前端现在**零运行时依赖**；本条要防的是开发期
  两端不同步，不是服务端撒谎（本地单机工具，前后端同一次构建出去）。
- **不引代码生成**（ts-rs / typeshare / utoipa）——后端没有响应 DTO，生成器只能覆盖直通子集。
- **不为三个哨兵写共享表**——判据见词条「镜像的两把刀」：它们属于「删镜像」那一类。
- **不动 `role` 存储列**。
