# 03: 台账里 assistant 行的「时刻」是开工时刻，不是说完时刻

**Status:** needs-triage
**Blocked by:** None (can start immediately)

**What happened（2026-10-08，班次 `01M4CDY9EC9M9FSSE236GJXYZC`）**：

- 每一对 `user` / `assistant` 行的 `created_at` 只差 **10–30 毫秒**——那不是「回得快」，
  是 assistant 行的时刻被写在了**这一轮开工**那一刻：409 用户 03:08:37.266 / 410 助手 03:08:37.296，
  而 410 那一轮实际跑到 03:08:50（它的提议落库时刻）。
- 更长的轮差得更远：394 那轮 00:48:23 开工、跑到 01:26:25（**38 分钟**）；407 那轮 02:12:49 开工、
  03:01:32 才落提交（**48 分钟**）。而会话的 `last_active_at`（收口那一刻刷）是 03:09:30。
- 机制：`created_at` 在 `begin_foreman_inflight`（建在途半截行）时就写死，收口的
  `close_foreman_inflight` 的 UPDATE **不刷它**（只刷 `last_active_at`）。
- **改成在途行之前**，assistant 行是收口时追加的（`created_at` = 说完时刻），而注释写着
  「台账最终形状与从前逐字一致」——这一格并不一致。

**影响面（为什么是 `needs-triage` 而不是马上改）**：对讲台时间线**不显示钟点**
（`Talk.svelte` 与 `talkTurns` 只用 `at` 排序），所以这不是界面 bug，是 **API / 审计层的口径**问题：
「谁说的、依据什么」这条可追溯链上，「说的时刻」被记成了「开工的时刻」。

**形状（待分诊）**：

- **(a) 让收口的 UPDATE 把 `created_at` 刷成收口时刻**——**荐**。它就是「这一行代表一次说话」
  该有的语义，也是改造前的行为；一并修正排序：一轮进行中落下的 `system` 行（例如「提议已执行」）
  今天会排在 assistant 行**之前**，刷成收口时刻后归位。开工时刻仍可从上一轮的收口时刻或
  本轮 traces / 提议的时间戳近似得到。
- (b) 另加一列 `started_at`、`created_at` 回收口时刻——最全（两个时刻都在），代价是一条迁移；
  若将来真要做「一轮跑多久」的读数，再从 (a) 升到 (b)。

**验收**（分诊选 (a) 时）：

- [ ] L2 集成：一轮的 assistant 行 `created_at` **晚于**同轮 user 行，且与 `last_active_at` 同刻
- [ ] L2 集成：在途期间（`status = 'in_flight'`）该行的 `created_at` 行为与今天一致（前端直播不受影响）
- [ ] L2 集成：一轮进行中落下的 `system` 行排在 assistant 行**之前**（时间序正确）
- [ ] 手工面：拿事故账班次重读 394 / 407 两行 —— 时刻应当是它们的收口时刻，不是 00:48 / 02:12
