### 问题五：成本软告警盯的是输出，而这一班的开销全在输入

**结论**：407 单轮 `prompt_tokens = 5,163,470` / `completion_tokens = 38,054`。判据是
`cost_verdict(is_watch, tokens.1, token_line)`（`runner.rs:1065`，`tokens.1` = **生成** token，
线 `FOREMAN_WATCH_TOKEN_BUDGET = 120_000`），整班一次没响。

**注意这是**明文裁决**，不是 bug**：决策 292 的原文就是「这一轮已烧 N **生成** token」，
立意是「人的那一轮无硬界，终点由你定」；轮数兜底 `FOREMAN_MAX_ROUNDS = 1000`。所以要动它是一条**新决策**。
另外 `prompt_tokens` 是这一轮里**每次模型调用 prompt 的累加**（`runner.rs:1120` `tokens.0 += response.prompt_tokens`），
不是单次调用的 prompt 大小。

```bash
$S "$DB" "SELECT sum(prompt_tokens), sum(completion_tokens) FROM kanban_foreman_messages
 WHERE session_id='01M4CDY9EC9M9FSSE236GJXYZC';"        # 12172916 / 217782
$S "$DB" "SELECT id, prompt_tokens, completion_tokens FROM kanban_foreman_messages
 WHERE session_id='01M4CDY9EC9M9FSSE236GJXYZC' ORDER BY prompt_tokens DESC LIMIT 3;"
$S "$DB" "SELECT count(*) FROM kanban_foreman_messages
```

### 问题六：合入把部署堵死（本班唯一的对外损伤）

**结论**：11:08:26 的合入把 106 的 `/opt/AgentPipeline`（**部署检出本身**）的 `main` 移到 `ba77558`
（parent `d4e11b9`），**1 ahead / 6 behind origin/main**，此后每次部署死在 `git pull --ff-only`。
修复分支是 08:25 从当时的 `origin/main`（`d4e11b9`）切出的，到 11:01 提交时 `origin/main` 已前进 6 个提交。

**根因**：`run_repair` **有** rebase 这一步（决策 212①，`foreman_actions.rs:121-123`），
但它的输入是本地的 `origin/main` **引用**；而**全仓唯一的 fetch 在建 worktree 那条路上**
（`git.rs:651` / `:699-703`），合入路径上不 fetch → rebase 判定「基准没动（no-op）」→ ff 把 `main`
移到旧基线上。提议 `situation_json` 里记着的 `base_commit: d4e11b9` **执行时一次没被读**。

```bash
ssh ... 'cd /opt/AgentPipeline && git log -1 --format="%h %ad %s" --date=iso ba77558 \
  && git log -1 --format="parent %h" ba77558^ && git rev-list --count d4e11b9..a7f4785'   # parent d4e11b9 / 6
$S "$DB" "SELECT situation_json FROM kanban_foreman_proposals WHERE id='01M4CQP6ZHCJQKMY672JPCZGFM';"
```

**为什么与 `deploy-divergence/01` 是两张票**：01 讲「**同一目录同时扮演两个角色**」（取材问题，
三条出路里的「独立克隆」能解它）；问题六讲「**基准新鲜度**」（读数问题）——即使把取材拆开，只要不 fetch，
合入照旧会落在一份陈旧基线上。见 [../deploy-divergence/issues/02-merge-on-stale-base.md](../deploy-divergence/issues/02-merge-on-stale-base.md)。

### 问题八：台账里 assistant 行的「时刻」是开工时刻（结构性口径）

## 四、被推翻的两处（我自己的）

取这份账时我自己有两条结论是错的，如实记，免得下一个人照着错的去查：

1. **「闸门与回执都不看基线」——错。** `run_repair` 合入前**先 rebase**（决策 212① 的既定机制，
   `foreman_actions.rs:121-123`），ff 那一支也是**真 ff**（`git.rs:1050-1061` 先判 `graph_descendant_of`
   再写引用）。真实缺陷小得多也准得多：**合入路径不 fetch**，rebase 的基准是一个没人刷新过的本地引用（问题六）。
2. **「收口时 diff 本来就在手上，所以改动最小」——错。** 收口那一刻 runner 手上只有 `traces` /
   `segments` / tokens / reply，**没有 diff、也没有改动文件清单**（`runner.rs:1545` 的 `live.close`）。
   便宜的路是**从 `traces` 的 `edit_file` / `write_file` 参数取路径**；repair 场景那份权威 diff 只有
   **调过 `finish` 的轮**才有（`{home}/worktrees/repair-{id}.diff` 与提议的 `payload_json`）。
