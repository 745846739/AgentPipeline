## 与规格的偏离（逐条给理由）

1. **提议表多两列**（`situation_json` / `claimed_at`）。前者是「执行时态势变了就拒执」这条规则的
   必需物（没有可比的指纹，那句话无从成立）；后者是「一次一按」的原子占用——四个 `status` 是
   **结局**的词表，把在途态塞进去会污染它（执行失败回到 pending 会看起来像状态抖动）。
2. **清单常量去掉 `FOREMAN_` 前缀**（`ENV_TOOLS` / `ENV_WRITE_TOOLS` / `SERVICE_WRITE_TOOLS`）。
   这道闸对**每一个**执行器生效（流水线阶段也有档位），只在值班长那一侧判就成了执行点上的
   per-caller 特例。已写进决策 206 的落地标注。
3. **`ENV_TOOLS` 比决策 206 的原文多一个 `delete_file`**。原文按「文件读写 + 命令」举例，
   漏掉它 `deny` 就是带门的墙。已标注。
4. **`ask` 档不允许配给非值班长阶段**（规格 §4 的要求，实现落在两条写入路径 + 表单筛选项）。
5. **`edit_file` 的 `old_text` 为空时拒绝**（本批顺带收紧）。空串会让替换变成「往文件开头插一段」，
   而回执说 `success`——一次**看起来成功**的错误改动。它不只影响值班长（流水线节点也会调这个工具），
   故这是一处**改变既有行为**的修正，已写进决策 207 的落地标注。
6. **`delete_file` 不给值班长**（`ENV_WRITE_TOOLS` 里有它，但 `FOREMAN_TOOL_SPECS` 里没有）。
   删除不可逆，决策 207 的清单没有它，本批也不给它开——若库里有一条旧提议带这个名字，
   执行会得到「这条提议的工具还没有接线」这句实话。
