## 0. 先把事实核对清楚（这是本条存在的前提）

| 说法 | 事实 |
|---|---|
| 「值班长只有两个只读工具，不符合最初的决策」 | 那两个工具（`read_task` / `read_conversation`）**正是**决策 182⑤ 与设计 Q12 明文定的（「工具只有两个、都只读」），且配了一条安全断言（`crates/core/tests/foreman.rs` 的「工具集恰为约定的两个」）。 |
| 「最初的决策」 | 更早的决策 50 / 附录 B.2 给**对话 agent**（v2 规划）配的是 `create_task`（自然语言建任务）+ 复用对话窗口。用户记的是**这一条线**——两条线在此处首次正面冲突：182⑤ 说「不动手」，50/B.2 说「能建任务」。 |

**故本条不是「实现漏了一个决策」，而是「两个决策打架，现在由用户裁定以哪条为准」。**

## 1. 裁决（决策 188）：三层意思

1. **工具集扩到 ZCode 级**：文件读写 / 命令执行 / `Skill` / 子代理等常用 agent 能力；
2. **再加上本系统全部接口功能**：建任务、恢复、拍板、合入、改配置、装技能、开关绑定……即把
   **API 面变成工具面**；
3. **写操作要人按确认钮**：模型不能直接执行写动作，只能在界面上生成一颗**确认钮**，由人按下。

**修订两处**：决策 182⑤（工具集不再固定为两个只读项）、决策 176④（「值班长的回复里**永远
没有按钮**」不再成立——确认钮正是要在它的回合里出现）。

**但 176④ 的要害不变**（这是本设计的第一约束）：

> `allowed_actions` 由后端下发、前端从不计算、**LLM 的判断绝不直接接进状态机**——这是全站唯一的
> 防错误放大接缝。

确认钮**不是**把这颗接缝拆掉：它是**人的**动作，模型只能**提议**；提议要经后端校验、由人按下、
再走**既有的那条**端点执行。模型永远拿不到「直接改状态」的能力。

## 2. 设计骨架

### 2.1 工具分三层，权限逐层收紧

| 层 | 内容 | 执行方式 | 需要确认钮 |
|---|---|---|---|
| **A 基座（只读）** | `read_task`、`read_conversation`（既有）+ `read_board` / `read_metrics` / `read_projects` / `read_stage_configs` / `read_skills` / `read_providers`（脱敏） | 直接执行，结果回灌 | 否 |
| **B 环境（ZCode 级）** | `read_file` / `list_dir` / `Skill`（按需拉技能正文）/ `spawn_sub_agent`（只读子代理） | 直接执行，仍受 `FileToolPolicy` 约束 | 否 |
| **C 环境（写）** | `write_file` / `edit_file` | **不直接执行**：生成提议 | **是** |
| **D 系统接口** | 每个端点一族：建任务 / resume / retry / cancel / 拍板 / 合入 / 改阶段配置 / 改 provider / 装技能 / 开关绑定 / 重置配对…… | 读端点直接执行；写端点**不直接执行**：生成提议 | 写=**是**，读=否 |
| **E `run_command`** | 命令执行 | 按权限模式走（决策 206）：`auto` 直接执行 / `ask` 生成提议 / `deny` 不广告且拒执 | `ask` 档=**是**；`auto` 档=否 |

**两张清单，不是一张**（决策 206）：`FOREMAN_ENV_TOOLS`（B / C / E 三层，档位可放开）与
`FOREMAN_SERVICE_WRITE_TOOLS`（D 层的写端点，**永不放开**）。**本服务的写接口恒为提议 + 确认钮，
不读档位**——把值班长配成 `auto` 只放开环境层（文件与命令），状态机写动作那一半不可取消。
两段清单与 `FOREMAN_TOOLS` 同姿态：**白名单在执行点强制**（`ToolExecutor::with_allowed_tools`），
任何「给值班长加个工具」的改动都要先改这里，从而在 diff 里显式可见。

**档位的域与默认**（决策 206）：值班长的域 = `home.root()`，`FileToolPolicy` **按路径前缀**把
`{root}/data` 与 `{root}/logs` 加进 deny（`data/agentpipeline.db` 明文存 provider 密钥，决策 112，
而 `.env*` / `*.pem` 那条模式名单盖不住它），默认档位 `ask`。`auto` 档下经 `run_command`
读走密钥库这条**无补偿**（文件策略不管命令，`cwd` 域对命令也几乎无约束——命令自己 `cd` 就出去了），
已登记进 `docs/operations.md` 的残余风险表并归入「等 OS 级沙箱」那一类（决策 206 修订
19（修订）/ 104 / 179 的接受面）。

### 2.2 确认钮：提议 → 落库 → 人按 → 走既有端点

```
模型发起写工具调用
   → 执行点拦截（不进真实执行）
   → 生成一条「提议」：{tool, 参数, 一句话说明, 过期时间}
   → 落库（新表，独立于 kanban_foreman_messages）
   → 对讲台时间线渲染成一张带确认钮的轮（复用急停轮的 .warn 形态与 PendingActions 的渲染）
   → 人按下「执行」
   → 后端按提议里的 (端点位, 参数) 走**既有端点那条路**（同一套校验、同一套闸门）
   → 结果回灌成一轮对话（成功 / 失败都进时间线，不弹窗）
```

四条硬约束：

1. **提议不是动作**：库里存的是「打算做什么」，执行必须经过端点的全部校验（依赖循环、worktree
   准入、写入门、fail fast……）。**不得**为值班长开一条绕过校验的捷径——否则「LLM 接进状态机」
   换个形式又回来了。
2. **过期即失效**：提议带 TTL（**10 分钟**，决策 207；比照 resume cooldown 的姿态），过期后按钮变灰并
   说明原因，**但那一轮留在时间线里**（审计价值：值班长当时提议过什么必须可追溯，与 `briefing_json` /
   `traces_json` 同一理由）；态势已经变化（任务状态 / `allowed_actions` 变了）的提议**拒绝执行**
   并报出「现在的情况已经不是它当时说的那样」。**重启后保留**：落库天然持久，只要未过期、
   `status` 仍 `pending`、态势未变即可执行——不另立「重启即作废」规则。
3. **一次一按**：提议执行成功后作废，不可重放（幂等由端点自己保证，提议层不重复触发）。
   **不做去重**（决策 207）：模型连着提两次就是两条、人各按一次；去重会让「我拒了它、它又提了一次」
   这个真实情形不可表达。
4. **与急停轮不重复**：同一个动作若已在状态区的急停轮里以 `allowed_actions` 的钮出现，
   值班长的提议**不另渲染第二颗钮**——改为一句指路（「这件事在状态区等你按键」，决策 176④的
   原顾虑「同一个动作两个位置各一颗钮」由此保留）。**这一条与「写功能需要确认按钮」不冲突**：
   该动作已经有钮了，只是那颗钮长在状态区。

### 2.3 数据与契约

- **新表**（迁移序号 **0015**，落地时以当时实际的空号为准——0012 归会话、0013 / 0014 归续接原因驱动）：
  `kanban_foreman_proposals(id, session_id, tool, args_json, summary, created_at, expires_at, status, resolved_at)`；
  `status ∈ {pending, executed, rejected, expired}`。`session_id` 是决策 204 的兑现点（提议挂在会话上）。
  TTL 10 分钟、重启后保留、不去重（决策 207，细则见 §2.2）。保留期接进既有清理作业
  （`runtime.rs:31` 的 `MAINTENANCE_INTERVAL`，每小时跑一次；与 `conversation_retention_days`
  同一口径——对讲台不做全仓唯一不设保留期的表）。
- **端点**：`GET /foreman/proposals`（未决提议，按 `session_id` 取）、`POST /foreman/proposals/{id}/execute`、
  `POST /foreman/proposals/{id}/reject`。三个都在局域网形态下受配对令牌护（决策 182⑦ 的既有口径，
  落在 `/foreman/` 前缀下自动继承）。
- **SSE**：提议到达 / 作废复用既有 `SseEvent::ConversationDelta` 之外**新增一个只读事件**
  （提议不是对话增量，混在一起会让前端的时间线归约变复杂）。
- **工具面与 API 面的映射**是**两张清单常量**（决策 206）：`FOREMAN_ENV_TOOLS`（环境层，受档位支配）
  与 `FOREMAN_SERVICE_WRITE_TOOLS`（本服务写端点，恒确认、不受档位），与
  `FOREMAN_TOOLS` 同一姿态：**白名单在执行点强制**，任何「给值班长加个工具」的改动都要先改
  这里，从而在 diff 里显式可见。**D 层的排除清单**（决策 207，三项）：重置配对令牌、局域网开关、
  仓名单（`kanban_market_repos`）增删——判据是「改的是**谁能访问这台机器**」，让模型能提议它们
  等于让它能给自己开门。

## 4. 待裁项（**已全部裁定**——2026-09-17，决策 206 / 207；四条并列如下，原「建议」保留以便对照）

1. **`run_command` 开不开？** 决策 182 明确把它排除过，理由是「值班长的输入是人可以随便打的任意
   文本」——它与文件读写不同：命令执行没有 `FileToolPolicy` 那样的窄边界，出口控制（决策 179）
   只约束「主动经 `run_command` 发起的调用」，明确**不是安全边界**（被启动的子进程后续自行联网
   在视野之外）。~~**建议：第一版不开**，等前三层跑顺了单独裁决。~~
   **已裁（决策 206 / 207）：开。** 走权限模式三档——`auto` 直通、`ask` 生成提议、`deny` 不广告且拒执；
   值班长默认 `ask`，档位可配但本服务写接口恒确认。**E 层因此不需要提议表**（只有 `ask` 档才生成提议，
   `auto` 档落命令日志）。182⑤ 那条排除理由**仍然成立**（域 = `home.root()`、`auto` 档可读走明文密钥库，
   无补偿），由用户知悉后接受，决策 206 已显式标注。
2. **`write_file` 的写域**：限定在工作区 / 任务目录内（`FileToolPolicy` 既有边界），还是允许写家
   目录下的配置？~~**建议：只允许任务目录内**——家目录下的配置改动走 D 层的接口工具（那有校验门）。~~
   **已裁（决策 207）：分两组。** 流水线阶段 agent 仍限任务工作区（不改）；值班长的域 = `home.root()`，
   由 `FileToolPolicy` 按前缀 deny 掉 `{root}/data` 与 `{root}/logs`（决策 206）。于是 `skills/` 与
   `market-repos/` 在值班长手里**可达**——那是「像 zcode 一样」的应有之义，要收紧就在 deny 前缀里加一行。
3. **确认钮的视觉落点**：进状态区（与急停并列，决策 183 的折叠规则需要扩一条）还是在对话时间线
   里内联？**已裁（决策 207）：内联在时间线的那一轮里**（原建议不变），复用急停轮的 `.warn` 形态与
   `PendingActions` 的渲染；与状态区已有的钮重复时**只渲染指路**，不画第二颗。后续由 §3.3 的视觉规格
   裁决档位（确认钮不得新开一档「响」——全站唯一告警仍是急停，决策 203）。
4. **工具的粒度**：D 层是「一个端点一个工具」（40+ 个工具，模型选择困难、token 成本高），还是
   「一族一个工具 + 动作参数」（如 `task_action(task_id, action)`）？**已裁（决策 207）：一族一个**，
   粒度对着 `allowed_actions` 的类型走，与既有动作集同构（原建议不变）。代价是模型可能选错动作，
   而确认钮正是为拦这个而存在。

## 6. 明确不做（第一版）

- 不做「模型自己执行写动作、事后告知」（那就是把 176④ 拆了）——**注意这里的「写动作」指状态机的
  写动作**（D 层的本服务接口）：`auto` 档放开的是环境层（文件与命令），状态机那一半**永不**放开
  （决策 206）；
- 不做提议的自动接受（确认钮的意义就是**每一次**都由人按）；
- 不做多步事务式的提议组合（一次提议 = 一个动作，组合由人连按几次完成）；
- 不给值班长开绕过 `allowed_actions` 的旁路（决策 69 / 101 的接缝不动）。
