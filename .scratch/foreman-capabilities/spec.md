# 值班长能力扩面：从两个只读工具到「能动手、但要人按确认钮」

**Status:** draft（**待评审**——决策 188 已定方向，实现设计未定形，本文件是它的提案）

> 来源：用户诉求「对讲台值班长只有 `read_task` 和 `read_conversation` 两个工具，不符合最初的
> 决策」，随后裁决（决策 188 原话）：「**像常用 agent 如 zcode 一样，另外再加上本系统内所有
> 接口功能，写功能需要确认按钮**」。
>
> **本文件不落代码。** 它修订的是两条载荷边界的决策（176④ / 182⑤），按本仓惯例要先出规格与票、
> 经评审再动手；在此之前**维持现状**（值班长仍是两个只读工具）。

## 0. 先把事实核对清楚（这是本条存在的前提）

| 说法 | 事实 |
|---|---|
| 「值班长只有两个只读工具，不符合最初的决策」 | 那两个工具（`read_task` / `read_conversation`）**正是**决策 182⑤ 与设计 Q12 明文定的（「工具只有两个、都只读」），且配了一条安全断言（`crates/core/tests/foreman.rs` 的「工具集恰为约定的两个」）。 |
| 「最初的决策」 | 更早的决策 50 / 附录 B.2 给**对话 agent**（v2 规划）配的是 `create_task`（自然语言建任务）+ 复用对话窗口。用户记的是**这一条线**——两条线在此处首次正面冲突：182⑤ 说「不动手」，50/B.2 说「能建任务」。 |

**故本条不是「实现漏了一个决策」，而是「两个决策打架，现在由用户裁定以哪条为准」。**

## 1. 裁决（决策 188）：三层意思

1. **工具集扩到 ZCode 级**：文件读写 / 命令执行 / `Skill` / 子代理等常用 agent 能力；
2. **再加上本系统全部接口功能**：建任务、恢复、拍板、合入、改配置、装技能、开关绑定……即把
   **API 面变成工具面**；
3. **写操作要人按确认钮**：模型不能直接执行写动作，只能在界面上生成一颗**确认钮**，由人按下。

**修订两处**：决策 182⑤（工具集不再固定为两个只读项）、决策 176④（「值班长的回复里**永远
没有按钮**」不再成立——确认钮正是要在它的回合里出现）。

**但 176④ 的要害不变**（这是本设计的第一约束）：

> `allowed_actions` 由后端下发、前端从不计算、**LLM 的判断绝不直接接进状态机**——这是全站唯一的
> 防错误放大接缝。

确认钮**不是**把这颗接缝拆掉：它是**人的**动作，模型只能**提议**；提议要经后端校验、由人按下、
再走**既有的那条**端点执行。模型永远拿不到「直接改状态」的能力。

## 2. 设计骨架

### 2.1 工具分三层，权限逐层收紧

| 层 | 内容 | 执行方式 | 需要确认钮 |
|---|---|---|---|
| **A 基座（只读）** | `read_task`、`read_conversation`（既有）+ `read_board` / `read_metrics` / `read_projects` / `read_stage_configs` / `read_skills` / `read_providers`（脱敏） | 直接执行，结果回灌 | 否 |
| **B 环境（ZCode 级）** | `read_file` / `list_dir` / `Skill`（按需拉技能正文）/ `spawn_sub_agent`（只读子代理） | 直接执行，仍受 `FileToolPolicy` 约束 | 否 |
| **C 环境（写）** | `write_file` / `edit_file` | **不直接执行**：生成提议 | **是** |
| **D 系统接口** | 每个端点一族：建任务 / resume / retry / cancel / 拍板 / 合入 / 改阶段配置 / 改 provider / 装技能 / 开关绑定 / 重置配对…… | 读端点直接执行；写端点**不直接执行**：生成提议 | 写=**是**，读=否 |
| **E `run_command`** | 命令执行 | **本设计建议先不开**（见 §4 待裁项 1） | — |

### 2.2 确认钮：提议 → 落库 → 人按 → 走既有端点

```
模型发起写工具调用
   → 执行点拦截（不进真实执行）
   → 生成一条「提议」：{tool, 参数, 一句话说明, 过期时间}
   → 落库（新表，独立于 kanban_foreman_messages）
   → 对讲台时间线渲染成一张带确认钮的轮（复用急停轮的 .warn 形态与 PendingActions 的渲染）
   → 人按下「执行」
   → 后端按提议里的 (端点位, 参数) 走**既有端点那条路**（同一套校验、同一套闸门）
   → 结果回灌成一轮对话（成功 / 失败都进时间线，不弹窗）
```

四条硬约束：

1. **提议不是动作**：库里存的是「打算做什么」，执行必须经过端点的全部校验（依赖循环、worktree
   准入、写入门、fail fast……）。**不得**为值班长开一条绕过校验的捷径——否则「LLM 接进状态机」
   换个形式又回来了。
2. **过期即失效**：提议带 TTL（建议 10 分钟，比照 resume cooldown 的姿态），过期后按钮变灰并
   说明原因；态势已经变化（任务状态 / `allowed_actions` 变了）的提议**拒绝执行**并报出「现在的
   情况已经不是它当时说的那样」。
3. **一次一按**：提议执行成功后作废，不可重放（幂等由端点自己保证，提议层不重复触发）。
4. **与急停轮不重复**：同一个动作若已在状态区的急停轮里以 `allowed_actions` 的钮出现，
   值班长的提议**不另渲染第二颗钮**——改为一句指路（「这件事在状态区等你按键」，决策 176④的
   原顾虑「同一个动作两个位置各一颗钮」由此保留）。**这一条与「写功能需要确认按钮」不冲突**：
   该动作已经有钮了，只是那颗钮长在状态区。

### 2.3 数据与契约

- **新表**（迁移 0010）：`kanban_foreman_proposals(id, tool, args_json, summary, created_at, expires_at, status, resolved_at)`；
  `status ∈ {pending, executed, rejected, expired}`。保留期接进既有清理作业（与
  `conversation_retention_days` 同一口径——对讲台不做全仓唯一不设保留期的表）。
- **端点**：`GET /foreman/proposals`（未决提议）、`POST /foreman/proposals/{id}/execute`、
  `POST /foreman/proposals/{id}/reject`。三个都在局域网形态下受配对令牌护（决策 182⑦ 的既有口径）。
- **SSE**：提议到达 / 作废复用既有 `SseEvent::ConversationDelta` 之外**新增一个只读事件**
  （提议不是对话增量，混在一起会让前端的时间线归约变复杂）。
- **工具面与 API 面的映射表**是一份**清单常量**（`FOREMAN_WRITE_TOOLS`），与
  `FOREMAN_TOOLS` 同一姿态：**白名单在执行点强制**，任何「给值班长加个写工具」的改动都要先改
  这份清单，从而在 diff 里显式可见。

## 4. 待裁项（**这四条没点头之前不该开工**）

1. **`run_command` 开不开？** 决策 182 明确把它排除过，理由是「值班长的输入是人可以随便打的任意
   文本」——它与文件读写不同：命令执行没有 `FileToolPolicy` 那样的窄边界，出口控制（决策 179）
   只约束「主动经 `run_command` 发起的调用」，明确**不是安全边界**（被启动的子进程后续自行联网
   在视野之外）。**建议：第一版不开**，等前三层跑顺了单独裁决。
2. **`write_file` 的写域**：限定在工作区 / 任务目录内（`FileToolPolicy` 既有边界），还是允许写家
   目录下的配置？**建议：只允许任务目录内**——家目录下的配置改动走 D 层的接口工具（那有校验门）。
3. **确认钮的视觉落点**：进状态区（与急停并列，决策 183 的折叠规则需要扩一条）还是在对话时间线
   里内联？**建议：内联在时间线的那一轮里**（它属于那次对话），然后由 §3.3 的视觉规格裁决档位。
4. **工具的粒度**：D 层是「一个端点一个工具」（40+ 个工具，模型选择困难、token 成本高），还是
   「一族一个工具 + 动作参数」（如 `task_action(task_id, action)`）？**建议：一族一个**，粒度对着
   `allowed_actions` 的类型走，与既有动作集同构。

## 5. 建议的切片（票，评审后细化）

```
01（基座）A 层只读工具补齐 + 白名单清单化 + 「工具集恰为 N 个」断言改写
02（提议）提议的存储 / 过期 / 执行端点 / 拒执语义（**不含任何新工具**——先把这条接缝单独跑通）
03（界面）确认钮的渲染 + execute/reject + 与急停轮不重复的指路
04（写）C 层 write_file / edit_file 接进 02 的接缝
05（系统接口）D 层写端点接进 02 的接缝（按领域分批：任务 → 配置 → 技能与市场 → 绑定）
06（兜底）E 层 run_command 单独裁决后落地（可能不做）
07（文档）人格 / 术语表 / 视觉规格 / 决策行修订收口
```

**02 必须独立成票且在 04 / 05 之前**：确认钮这条接缝是整批的承重墙，它跑通之前加任何写工具都是
在赌。

## 6. 明确不做（第一版）

- 不做「模型自己执行写动作、事后告知」（那就是把 176④ 拆了）；
- 不做提议的自动接受（确认钮的意义就是**每一次**都由人按）；
- 不做多步事务式的提议组合（一次提议 = 一个动作，组合由人连按几次完成）；
- 不给值班长开绕过 `allowed_actions` 的旁路（决策 69 / 101 的接缝不动）。
