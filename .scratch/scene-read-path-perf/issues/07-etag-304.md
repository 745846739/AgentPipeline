# 07: ETag / 304——回看已完成任务时不再重搬

**What to build:** 用户的痛点是「每次打开同一个任务都等几秒」，而任务内容在两次打开之间
**常常没变**。给两个端点的响应加 `ETag` + `If-None-Match` 协商，命中就回 **304（零字节）**：

- `GET /tasks/{task_id}/conversations`（含票 03 加的 `include_messages=true` 分支）——
  现场页签的全部载荷就在这里；
- `GET /tasks/{task_id}` —— 详情页的头部/游标/动作。

**收益集中在「回看已完成任务」**：跑着的任务每次都变，跑完的则完全不变。改动后可把
`/commands`（票 02 已移出首屏、票 01 已压缩）与批量会话在重复打开时降到 0 字节。

**Blocked by:** 01, 02, 03（票 03 引入批量读法是 ETag 的主要受益面；票 01/02 先落地才
看得出 ETag 的边际收益还剩多少）

**Status:** ready-for-agent

## 落点

- `crates/app/src/routes/tasks.rs`：两个 handler 计算版本键 → `ETag` 响应头，
  读 `If-None-Match` 命中则 304（注意 304 不回 body，但必须保留 `ETag` 与缓存相关的头）。
- **版本键的坑（必须处理）**：会话摘要的 `status` 字段是从台账 `list_runs` 贴进来的
  （`tasks.rs:843-852`），所以**一个 run 从 `running` 变 `done` 时，会话列表的 ETag 必须变**
  ——只用「会话行数 + MAX(id)」当版本键会漏掉这次变化。版本键至少要覆盖
  `(conversations 的 MAX(id), 行数, include_archived 布尔, runs 的状态集合)`，
  或退而求其次对响应体取哈希。
- 别给流式响应（SSE）加 ETag。

## 验收

- [ ] 第二次打开同一个**已完成**任务：`/conversations`（含 messages 分支）命中 304，
      `size_download` 为 0，页面数据照常显示（浏览器复用缓存）
- [ ] **跑着的任务不会拿到过期 304**：一个 run 从 `running` 变 `done` 之后，同一 `If-None-Match`
      必须拿到 200 与新内容（这是本票最容易写错的判据，要有测试）
- [ ] 不同 `include_archived` / `include_messages` 组合给出**不同** ETag（参数参与版本键）
- [ ] SSE 路由不带 ETag，且直播行为不变
- [ ] `make api` 契约测试覆盖 200 / 304 两条路径；`make check` 全绿

**明确不做**：`Cache-Control: max-age` 强缓存（任务内容会变，强缓存会给出过期数据；
只做协商缓存）；给 `/commands` 加 ETag（票 02 已把它移出首屏，边际收益低——若后续发现
现场页签的命令部分值得，再另开）。
