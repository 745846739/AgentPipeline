# 03: 共享 CARGO_TARGET_DIR + worktree 构建产物回收(B5 收口)

**What to build:** 「混合模式」的本机半边:交互式走查留在 106,走查所需的 debug 构建
不能外发(产物不回传,106→GitHub 实测仅 ~197KB/s),只能本地提速。做法:各任务 worktree
的构建产物收敛到共享 target 目录(而非每 worktree 一份 1.4GB),任务归档/done 时对
共享目录有确定性的回收路径(定期清理或水位上限)。做完后 40G 盘不再被
「几个跑过构建的任务叠加」吃穿,增量构建因共享缓存压到分钟级。

**Blocked by:** None(可立即开始;与 GitHub 侧 04/05/06 完全独立)

**Status:** ready-for-agent

- [ ] 任务 worktree 内的构建走共享 target 目录,连跑两个构建类任务,
      worktree 自身不再出现整份 target/ 增长
- [ ] 任务归档/done 时构建产物有确定回收路径(机制保证,不依赖「恰好被清」——
      01M3X472FJF8NW9082K6BFZPKC 那次的教训)
- [ ] 40G 盘在连续多个构建类任务后水位有界;清理不影响在跑任务
- [ ] 走查「改码→可走查」的本地增量构建实测不劣于改前基线(借助 01 的工具日志计时)

> **实现注记(2026-10-02,code review 后定稿)**:
> ① 回收带**非阻塞占锁哨兵**(`shared-target/.prune-lock`):拿不到锁 = 有任务在构建,
>   本次跳过留 WARN——「清理不影响在跑任务」由机制保证,不靠时序运气;锁文件常驻不删
>   (删了是持锁 inode 与后来者不一致的经典竞态)。
> ② **并发排队语义已写进 runner_for 的注释**:多任务并发构建在 cargo 文件锁上零进度
>   排队,任务命令缺省 60s 超时可能被排队吃光——构建类命令本就该显式传 timeout_sec
>   (走查跑 e2e 传 7.5 分钟是既有实践);闸门侧 600s 覆盖排队绰绰有余。
> ③ 「40G 盘水位有界」与「增量不劣于基线」两条要在 106 真任务上实测收口(部署后)。
