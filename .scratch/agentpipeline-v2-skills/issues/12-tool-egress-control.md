# 12: `run_command` 工具层出口控制

**What to build:** 给 `run_command` 增加**网络策略**：默认按 allowlist 放行，未放行的目标需显式批准。
这是「市场下载的技能 + agent 有无限 shell」这一组合的唯一技术兜底。

**必须诚实标注残余风险**：工具层策略**只能约束 agent 主动经由 `run_command` 发起的调用**，约束不了
被启动子进程后续自行联网。本项的真实价值是「拦截直白的 exfiltrate 指令」，**不是安全边界**。

**Blocked by:** 10（远程 registry——「下载来的技能」这个威胁面是它引入的；本地导入的技能来自用户
自己的机器，不构成同一类风险）

**Status:** ready-for-agent

- [ ] 网络策略形态落地：默认 allowlist，未放行目标需显式批准（具体为命令级特征识别或网络层拦截，
      实现时选定并记录理由）
- [ ] 策略受配置控制，且**默认姿态保守**（未配置时不得静默变成「全部放行」）
- [ ] 被拒绝的调用有可归因报错与审计记录（落 `kanban_node_commands`，与既有命令日志同表）
- [ ] **残余风险写进文档**：约束不了子进程自行联网；不是安全边界。四家主流 agent 都靠
      OS 级沙箱 + 网络代理实现默认拒绝，而本仓结构上没有这层
- [ ] **OS 级沙箱（Seatbelt / bubblewrap）登记为后续决策的正式候选**，不在本票实现
- [ ] 单测：放行 / 拒绝 / 白名单边界样本；策略单测体例照 `file_policy.rs`
- [ ] 与决策 19（修订）/ 104 的关系在实现结论里点明：**不引入 OS 级沙箱**，只加工具层策略

**Notes（实现提示）:**
- 文档措辞要避免制造虚假安全感——四家产品的公开文档都在强调这一点（Claude Code
  「no system is completely immune」、Cursor「Auto-review is not a security boundary」）。
- 本票的安全价值与「技能根不得放宽为 agent 可读」是同一类边界收紧（后者由票 07 承担）。
