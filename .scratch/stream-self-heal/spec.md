# 实时流断线自愈:锁屏解锁、网络闪断都要自己接回来

**Status:** done（票 01–04 全部落地）

**Slug:** `stream-self-heal`

**来源:** 2026-09-24 用户问「移动端页面在锁屏再解锁后是否存在网络问题,需不需要重连」的诊断。
结论:锁屏必然断流,而「解锁 → `visibilitychange` → 立即重连 + 全量校准」这条主链**已经在**
(design §9.1,连接层的 `reconnectNow` + `StreamManager` 的可见性处理,单测已钉);本 spec 针对的是
诊断出的**三个残余缺口**与取证空位——服务端无心跳、前台半开连接无看门狗、对讲台没接校准回调,
外加一条 e2e 把「解锁恢复」端到端钉死。

---

## Problem Statement

用手机看 AgentPipeline 的人会锁屏:看任务看到一半按电源键、走开一会儿让屏幕自己灭、
解锁回来接着看。现在这条路上有四个问题:

1. **锁屏期间发生的事,解锁后不一定补得上。** SSE 没有回放,断流期间的阶段迁移、pending
   迁移全都丢了。现有的补救是「重连成功后主动校准一次」,但**解锁瞬间那次校准和重连是并发的**:
   如果校准请求因为网络还没醒而失败、紧随的重连却成功了,系统会认为「没有错过」,断流期间的
   变化就停在旧画面里,要等下一条事件或手动刷新才补上。
2. **网络闪断时,界面会说谎。** 屏幕亮着的时候 Wi-Fi 切换、路由抽风,会产生半开连接:
   fetch 的流读取可能挂死很久不报错,连接状态一直显示「已连接」,但再也没有新事件进来。
   看板有 10 秒对齐 tick 兜着,**任务详情页和对讲台没有任何周期兜底**,内容就一直 stale,
   断线横幅也不会出现。
3. **服务端从不发心跳。** 两个 SSE 端点都是「有事件才出字节」,一条安静的流在半开状态下
   双方都察觉不到——这正是问题 2 能长期存在而不被发现的原因。
4. **对讲台断线重连后不校准。** 它只在 `visibilitychange` 时 reload;流因为别的原因
   (非可见性变化)断掉再接回来,中途错过的对话增量不会补,必须切走再切回来才对齐。
5. **「解锁后会恢复」这件事没有端到端证据。** 现有 e2e 只钉了「掐断 SSE 出现断线指示」,
   没有一条测试证明「解锁 → 重连 → 校准」这条用户最常走的恢复链真的通。

## Solution

给实时流补上「断流必被发现、必被接回、接回必校准」三件事,用户视角:

- **锁屏解锁后,页面自己恢复。** 解锁触发可见性恢复:立即重开流 + 立即校准;而且**只要
  走过一次主动重连,重连成功后必定再校准一次**——第一次校准哪怕失败也有人兜底,断流期间
  的变化解锁后一定补得上,不用手动刷新。
- **网络闪断时,页面在有限时间内自己发现并接回。** 服务端每 15 秒发一个心跳帧;
  客户端在「已连接」状态下超过阈值收不到任何字节,就判定线已死、主动重连。健康但安静的
  连接不会被误杀(心跳字节就是「线还活着」的证据);看板、详情页、对讲台三处一视同仁。
- **对讲台与其它页面同等对待。** 流重连成功后也做一次全量 reload,不再依赖「切走再切回来」。

实现不改 SSE 的语义(仍无回放、靠校准补齐——决策 76),不改断线横幅与状态机的形状,
不新增可测试性接缝;三条接缝全是既有的,并补一条端到端取证。

## User Stories

1. 作为手机上看着任务详情再锁屏的人,我希望解锁后实时流自动重连,而不是手动刷新页面
2. 作为锁屏期间错过了阶段迁移的人,我希望解锁后页面自动补上断流期间的变化,而不是停在锁屏前那一刻
3. 作为解锁瞬间网络还没连上的人,我希望页面自己退避重试直到网络就绪,而不是卡在「断线」横幅上
4. 作为开着详情页遇到网络闪断的人,我希望有个看门狗发现流其实已经死了并重连,而不是一直显示「已连接」却收不到新事件
5. 作为开着对讲台遇到网络闪断的人,我希望看门狗同样替我发现死流,因为对讲台没有周期 refetch 兜底
6. 作为对讲台的值班经理,我希望流断线重连后做一次全量 reload,不必切走再切回来才知道错过了什么
7. 作为对讲台的值班经理,我希望解锁回来时和详情页一样立即重连 + reload
8. 作为回话进行中锁屏的人,我希望解锁后的 reload 接得上进行中的那一轮,而不是停在半截
9. 作为看板的用户,我希望 10 秒对齐 tick 照旧兜底状态迁移,这次改动不去动它
10. 作为网络不稳的人,我希望解锁时的重连失败按既有指数退避重试,且每次解锁都重置退避、不越等越久
11. 作为界面的使用者,我希望断线期间的横幅照旧出现、重连成功后消失,且**消失的同时内容已经校准**,而不是只换了张脸
12. 作为开了多条流的人(看板多任务),我希望每条流独立检测、独立重连,一条卡死不拖累另一条
13. 作为桌面本机用户,我希望这套机制在回环形态同样生效,不因局域网/配对形态分叉
14. 作为局域网配对形态的用户,我希望每次重连仍重读配对令牌,「先 403、后配对成功」的路照旧能自己走通
15. 作为维护者,我希望服务端每 15 秒发一个不携带数据的心跳帧,让任何半开连接在有限时间内暴露
16. 作为维护者,我希望心跳帧不带 data,客户端解析器一行不用改
17. 作为看门狗的实现者,我希望「收到任何字节」都算线还活着(心跳也是字节),把安静但健康的连接和死流分开
18. 作为测试维护者,我希望看门狗的阈值可注入、用假时钟驱动,不真等 45 秒
19. 作为测试维护者,我希望契约测试在一个**静默**的流上断言心跳按时到达,不依赖业务事件恰好发生
20. 作为测试维护者,我希望 e2e 有一条「掐断流 → 模拟解锁 → 断言校准请求与流重开」的取证,不再只靠肉眼验收
21. 作为跑全量测试的人,我希望四门(单测/契约/e2e/全量复跑)照旧全绿,既有测试一条不删
22. 作为实现者,我希望不新增可测试性接缝——决策 143 的权威表不因此加行
23. 作为维护者,我希望状态机形状不变(idle/connecting/open/closed/error),看门狗复用既有状态不发明新状态
24. 作为维护者,我希望「监听 online/offline 事件」明确写进不做清单,避免与看门狗形成两条互相掩盖的恢复路径

## Implementation Decisions

- **改动面只有三处模块**:SSE 连接层(分帧、退避、主动重连、可见性处理那一层)、
  两个 SSE 端点(任务流与值班长流)、对讲台的流处理器接线。看板的对齐 tick、断线横幅、
  状态机、配对令牌读取路径均不动。
- **服务端心跳**:两个 SSE 端点都开启 keep-alive,间隔 15 秒。心跳是**不携带 data 的帧**,
  客户端解析器只认 data 行,天然忽略——解析器与事件形状零改动。两处端点必须同做,
  否则值班长流成为漏网的那条。
- **客户端停滞看门狗**:连接层在 `open` 状态下按「**最近一次收到任何字节**」计时,
  超过阈值即判定死流并走既有主动重连路径(重置退避、中断旧连接、立即重开)。
  计时单位是字节到达而非「解析出事件」——心跳帧没有事件但有字节,这正是把
  「安静且健康」与「安静且已死」分开的判据。阈值 = 3 × 心跳间隔(45 秒),
  作为连接层的可注入选项(先例:既有的退避参数注入)。`connecting` 阶段不归看门狗管
  (那一段由 fetch 自身失败 + 退避兜底);`stop` 时看门狗随之清除。
- **修解锁竞态**:主动重连(可见性恢复触发的那条)一律置「断过线」标记,
  重连成功后**必定**补一次全量校准。现状是主动重连不置标记、靠可见性回调里那次并发的
  校准请求兜底——那次请求可能先失败而重连成功,竞态由此而来。改后可见性回调那次校准
  降级为「先到的预热」,重复校准无害,失败的那次有人接。
- **对讲台接上校准回调**:流重连成功后的补校准走它既有的 reload 入口(与可见性恢复
  分支同一入口),不另造第二条读路径。
- **心跳与看门狗的参数成对**:看门狗阈值必须显著大于心跳间隔(3 倍关系),
  两个常量在文档上互相引用,改一个必须看另一个——否则慢网络下会把健康连接误杀。
- **SSE 语义不变**:仍无回放、靠校准补齐(决策 76 的唯一状态入口地位不动);
  fetch 流式读取不用 EventSource(决策 153②)不动;每次重连重读配对令牌(决策 182)不动。
- **不新增可测试性接缝**(决策 143 权威表不加行):看门狗与重连落在连接层既有单测面,
  心跳落在既有契约测试面,解锁恢复落在既有 resilience e2e 面——三处全是既有缝。
- **`online`/`offline` 事件监听明确不做**:看门狗 + 可见性恢复已覆盖同一场景,
  两条恢复路径会互相掩盖问题(一条把连接重启了,另一条就永远测不到自己的分支)。

## Testing Decisions

- **好测试只断言外部行为**:「第二次 fetch 发出了」「校准回调被调用了」「心跳帧在
  间隔 + 余量内到达了」「断言期间没有任何业务事件」——不断言内部计数器、不断言私有字段。
- **接缝 A(客户端单测,既有)**:realtime 连接层单测(`connection.test.ts`)的既有形态
  ——jsdom + stub `fetch` + 真 `ReadableStream` + `vi.waitFor`/假时钟。新增用例:
  ① `open` 后静默到阈值 → 必须发起第二次连接;② 阈值内收到任意字节(哪怕是心跳) →
  不重连;③ 主动重连成功后 → 必须触发校准回调(解锁竞态的钉子);④ `StreamManager`
  派发 `visibilitychange` → 每条流都校准 + 重连;⑤ 阈值注入生效(用小阈值快测,
  不真等 45 秒)。先例:该文件里 `reconnectNow` 后断言第二次 fetch 的那条。
- **接缝 B(服务端契约,既有)**:`crates/app/tests/integration/api_contract.rs` 的既有形态。
  新增用例:分别连上任务流与值班长流,**不触发任何业务事件**,断言在 keep-alive 间隔 +
  余量内收到心跳帧(content-type 仍是 `text/event-stream`)。先例:同文件里
  `stream_is_the_only_event_channel_and_carries_branch` 与
  `foreman_stream_carries_conversation_deltas_to_subscribers` 两条——它们已经建立了
  「真连 SSE、断言帧」的姿势,心跳只是把「恰好有事件」换成「故意没事件」。
- **接缝 C(e2e,既有)**:`frontend/e2e/ux2-resilience.spec.ts` 的既有形态——
  `page.route` 掐断 SSE 的先例(票 13 那条)。新增一条:阻断流 → 页面派发
  `visibilitychange`(模拟解锁)→ 断言发起了全量校准请求(refetch)且流被重新打开
  (对同一路径的第二次请求)。真 axum 后端 + mock LLM + 临时 home,只 Chromium(决策 144)。
- **对讲台的校准接线**若难以在接缝 A 单测(Svelte 组件挂载),由接缝 C 的解锁用例
  在对讲台路由上覆盖——**不为此新设第四个缝**。
- **回归底线**:既有测试一条不删;四门全绿。

## Out of Scope

- **`online`/`offline` 事件监听**——与看门狗、可见性恢复重复,双路径互相掩盖(见上)。
- **WakeLock / 阻止锁屏**——那是跟操作系统要特权,不是网络问题的正解。
- **SSE 事件回放 / Last-Event-ID 断点续传**——SSE 语义保持「无回放、靠校准补齐」(决策 76)。
- **看板 10 秒对齐 tick 的任何改动**——它是状态迁移兜底,与连接兜底各司其职。
- **断线横幅文案与状态机形状的改动**(ux-audit-2 票 13 已有形态保持)。
- **分享页**——只读形态,无实时流订阅。
- **桌面壳特化行为**——本 spec 的机制在回环与局域网形态一视同仁,不为桌面壳单开分支。
