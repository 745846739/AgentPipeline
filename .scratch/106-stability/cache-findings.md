# prompt cache 验证实验（票 05 / 决策 380）

**结论先说**：106 在用 provider 的**前缀缓存早就在命中**，而且命中得非常好——
事故那 7.6 小时里整站 prompt token 的 **95.7% 是缓存命中**，事故任务自己
（`01M3X472FJF8NW9082K6BFZPKC`）是 **97.3%**。票面担心的「重喂按全价计费」不成立：
真正烧钱的不是单价，是**体量**（13M token / attempt × 9 次重入），而那正是票 03 治的。
组装层已经是缓存友好的（稳定头 + 只追加 + 固定工具序），故本票**不改生产代码**，
只把这份性质钉成回归测试（`RequestPlan` 组装确定性、适配器出口的「下一轮是上一轮的
前缀延长」、以及缓存读数落 run 行三条），并在下面留一份基线，供票 08 首小时监控对照。

## 一、provider 与字段口径

| 项 | 值 |
|---|---|
| 106 在用 provider | `deepseek/deepseek-v4.1-flash` |
| 端点 | `https://api.commandcode.ai/provider/v1`（OpenAI 兼容网关） |
| 响应里的命中字段 | `usage.prompt_tokens_details.cached_tokens` |
| 本仓解析点 | `agent/providers/openai.rs`（读的正是这个字段）→ `AgentResponse.cache_read_tokens` |

**一手探针**（2026-10-03，在 106 上就地跑，密钥不出服务器，只打印 `usage`）：
同一个定长 system 前缀发两次，第二次在它之后追加两轮：

```
请求 1：prompt_tokens 608，cached_tokens   0     ← 冷启动
请求 2：prompt_tokens 617，cached_tokens 512     ← 同一前缀，命中 512 / 617
```

两个读数：

- 缓存**按 token 前缀**命中，与消息列表的追加形态天然契合；
- 命中量 512 是 64 的整数倍，与「上游按固定块对齐、只算整块」的形状一致。
  （**一次读数钉不死块大小**——64 是从这一条推的，留作待复核的观察，不是结论。）
  可推出的是：头一段变了并不必然让整段作废，但会让**从该点往后的全部块**作废。

## 三、跨 attempt 的长间隔：超时梯子的 90 分钟熬得住吗

这是本票最该问的一个问题——超时梯子每档之间隔着几十分钟，若缓存 TTL 短于这个间隔，
那「干净重试」每一轮的首个请求都要全价重读。事故任务的 develop/execute **每个 attempt
的首个请求**（`seq = 1`）：

| attempt | 与上一 attempt 的间隔 | prompt | cache_read |
|---:|---:|---:|---:|
| 3 | 90 分钟 | 3,033 | 2,112 |
| 4 | 41 分钟 | 2,701 | 2,688 |
| 5 | 49 分钟 | 2,701 | 2,688 |
| 6 | 38 分钟 | 2,701 | 2,688 |
| 7 | 25 分钟 | 2,701 | 2,688 |
| 8 | 90 分钟 | 2,705 | 2,688 |
| 9 | 90 分钟 | 2,701 | 2,688 |

**六次连续命中，间隔 25–90 分钟不等**（2688 就是那一段 system prompt 的命中量）。
结论：**在这个时间尺度上缓存不会被熬死**，梯子的间隔不是缓存杀手。
（上游文档口径：不用即清，「usually within a few hours to a few days」。）

## 四、组装层为什么已经友好（本票钉住的三条）

1. **头是稳定的**：[system][user][载入的历史][本轮追加] —— `openai.rs` 的出口顺序；
   `AttemptCtx` 里没有任何时间戳 / run 号 / 计数进入 system 或 user
   （`template_vars` 全部取自库与路径）。
2. **转录只追加**：`model_invoke` 的轮循环只 `messages.push(...)`（assistant → tool_result），
   从不回头改口，也不在头部插东西。决策 279 早已把「用户补充输入」从首条 user 挪成
   转录末尾的 user turn，就是这个理由。
3. **工具顺序确定**：`effective_tools` = 基线常量的顺序 + 声明顺序（去重保位）；
   技能目录走 `BTreeMap`（按名字排序）——没有一处 `HashMap` 迭代序漏到 prompt 上。

本票把这三条钉成**回归测试**（生产代码一个字不改）：

- `model_request::assemble_freezes_a_byte_stable_head_and_a_fixed_tool_order`
  —— 同一输入两次组装逐字节相同；工具序 = 基线常量序 + schema 工具收尾。
- `providers::openai::the_next_round_is_a_prefix_extension_of_the_previous_wire_messages`
  —— 第 N+1 轮的 wire 消息头**是第 N 轮的整段原样**（缓存只认这个）。
- `executor::provider_cache_readings_land_on_the_run_row`
  —— 替身模拟「第 1 轮冷启动、此后命中」，命中的读数要原样落 run 行
  （详情页与滚动投影读的都是这一份）。

## 五、计费折扣与节省比例（给出口径，不给承诺）

命中 token 的单价远低于未命中（上游 DeepSeek 定价页 2026-10-03 读取：命中与未命中
之比在 **1:30–1:50** 量级），但**本仓不做计费口径**（票面边界：`run_tokens` 仍是
prompt+completion，cache 单列）。网关（commandcode.ai）自己的账单口径不在这份证据里，
需要精确金额时以 provider 账单为准。

**节省比例（按上表算，条件写在式子里）**：设命中价为未命中的 `1/k`，实测命中率
`h = 0.9568`，则 prompt 侧的有效成本是无缓存时的 `(1-h) + h/k`：

| 若 k = | 有效成本 | 相对无缓存省下 |
|---:|---:|---:|
| 10 | 16.6% | 83.4% |
| 30 | 7.5% | 92.5% |
| 50 | 6.2% | 93.8% |

即：**prompt 侧账单已经压到无缓存时的 ~6%–8% 量级**（在 k = 30–50 的假设下）。
k 是上游厂商标价，不是本机网关的账单——**这个比例跟着 k 走，别当承诺用**。

## 五之二、失败形态（命中不了的几种场合）

| 形态 | 现场读数 | 能不能治 |
|---|---|---|
| **冷启动** | 每条 run / 每个 attempt / 每个新班次的第一条请求必然 `cached_tokens = 0`（事故任务 develop.execute 的 attempt 1 命中率 90.5%，其余 attempt 都 ≥94.9%） | 治不了——第一份没有前缀可匹配 |
| **部分块落空** | 命中量只算整块，尾巴那点不满一块的照价计（探针里 617 命中 512） | 治不了，量也小 |
| **长间隔过期** | 上游口径「不用即清，usually within a few hours to a few days」；本仓实测**跨 90 分钟仍命中**（第三节） | 不是本仓的瓶颈，不动 |
| **前缀被改写** | 本仓只有一处会改写转录前缀：L3 压缩（票 03）。每压一次，被压掉那段的下游全部作废 | 是设计取舍（体量换命中），不是缺陷——见第六节 |
| **网关路由漂移** | 未观察到。探针只发了两次、历史账单也读不出「同一前缀突然不命中」的形态 | **证不了也否不了**（n 太小），留作观察项 |

## 六、与票 03 的相互作用（留给票 08 的一次对照）

压缩与缓存是**反向**的：L3 每压一次，「被压掉的那段」下游的全部块立刻作废。票 03 把
硬底接上之后，压缩会**更频繁**地发生——命中率有掉一点的可能。这是有意的取舍
（**体量换命中**：压掉 40 万字符省下的绝对量，远大于它作废的那点前缀），不是回归。

上面 95.68% 是**票 03/04 部署之前**的基线。票 08 重建任务后首小时监控时，顺带跑一次：

```sql
select round(100.0*sum(cache_read_tokens)/max(1,sum(prompt_tokens)),2)
  from kanban_model_requests
 where started_at > '<重建时刻>';
```

**低于 ~85% 才值得回头看组装层**；90% 上下属于压缩的正常代价。

## 七、明确不做

- 不做缓存键的手工管理（provider 自动前缀匹配）；
- **不**为了让前缀更稳而重排 prompt 分层（把易变段从首条 user 挪到转录末尾）：
  数据不支持——跨 attempt 已经命中 25–90 分钟不衰，重排是一处**行为改动**，
  没有证据支撑，留待将来真有命中塌陷的现场再说。
- 不改计费口径、不动 `offload_threshold_tokens` / L1 口径。
