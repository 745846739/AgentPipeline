# 主流程端到端可信度（agentpipeline-mainflow-e2e）

## 目标

让「一条端到端测试全绿」这句话**对用户主流程有真实含义**。当前 `frontend/e2e/` 的两条
playwright 用例（票 18）覆盖了主流程中段，但入口、产物形态、真实失败模式三处与用户实际
使用不对齐，因此存在「测试全绿、用户一上手就卡」的窗口。本 effort 把所有已识别缺口落成票面，
按优先级补齐，使主流程的每一段都有端到端证据。

**验收口径（本 effort 的定义）：** 用户从「装好启动」到「看到合入结果」的主流程上，
每个不可避免的环节都有一条会真跑的端到端用例；非主流程分支要么有用例、要么在票面显式登记为已知风险。

## 优先级

| 优先级 | 票 | 为什么这个顺序 |
|---|---|---|
| P0 | 01 浏览器走真实产物 | 决定的不是「多测一个分支」，而是**现有两条用例测的是用户不会走的那条入口**；且它是 05–10 的公共前置 |
| P0 | 02 闸门真跑 | 用户必然经过、当前完全盲；且短路的是主流程里的失败分流逻辑 |
| P0 | 03 配错可恢复 | 真实使用最高频的失败点，当前界面只回显原始错误串 |
| P0 | 04 真模型全流程手跑 | 唯一能覆盖「真 LLM 返回格式」的手段；把「无人知晓」变成「发版前有人确认」 |
| P1 | 05 UI 三步创建 | 主流程入口，当前零覆盖 |
| P1 | 06 人工评审分支 | 主流程正常分支（新建任务时可勾选），当前零覆盖 |
| P1 | 07 日志/对话内容 + 刷新 | 用户高频动作；当前只验「页签能点」 |
| P2 | 08 真进程重启 | 风险真实但触发条件低（用户会关终端/重启） |
| P2 | 09 并发第二任务 | 单任务 happy path 之外的常见真实用法 |
| P2 | 10 闸门与产物新鲜度 | 决定前面所有票的结论是否可信 |

├── 02 闸门真跑

├── 05 UI 三步创建

01 是单点瓶颈，因此**先做 01，其余 9 张并行可取**。04 不依赖 01。

## 关键约束

- 与决策冲突须显式标注编号（AGENTS.md）。
- 每票验收落在既有质量闸门内：`cargo fmt --check`、`clippy --workspace --all-targets -- -D warnings`、
  `cargo test --workspace`；涉及前端加跑 vitest / svelte-check / build 与 `just frontend-e2e`。
- **替换边界不变**（决策 148 / 151）：只替换 LLM 响应流，工具 / git / 命令 / 策略全部真跑。
- **只 Chromium**（决策 144）。
- 不得为通过测试而弱化决策 104 / 118 / 128 / 157 的安全语义。

| 真 LLM 进自动门 | 决策 142 已裁决只保留 `#[ignore]` 手动冒烟——外部不确定性不做回归门。票 04 遵守此边界 |

| 性能 / 负载 | 决策 144 |
