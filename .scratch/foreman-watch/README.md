## 四条不可换的顺序

1. **证据面在前**（01–03）：没它，值守只能盲诊。诊断包是「能分析出代码 / prompt / 环境问题」的
   前提，而它不是「多读几个字段」——失败会话落库与 prompt 原文落库是数据模型层面的两件事。
2. **08「托管」排在 03 之后**：托管是唯一让值班长能免按键动状态机的东西（§4.2 的破坏性例外），
   而它必须以诊断能给出可归因结论为前提。否则等于让一个盲诊的值班长动手。
3. **09「unstick」排在 08 之后、10 之前**：`resume` 要能真的生效，得先能把进程内去重里那个
   `task_id` 摘掉。2026-09-17 那次「超时后重试没发生」就是这个前提缺失的实证。
4. **先改断言再加能力**（03 与 08）：两条断言钉着被本批改写的边界——`crates/core/tests/foreman.rs`
   的工具集冻结断言（`:598-632`）与 D 层恒提议断言。`foreman.rs:56-59` 的原话：
   「这是安全边界本身，不是配置项」。

## 开工前已落地的一件事（非票）

`crates/core/src/git.rs`：`GIT_OP_TIMEOUT_SEC = 180` / `IS_DIRTY_TIMEOUT_SEC = 10` /
`blocking_within`，`do_init` 的脏工作区检查改为 best-effort（`executor.rs:387-405`）。
来历是 2026-09-17 的实测——`支持rtk` 任务「一创建就永久卡在 init」，根因是 `do_init` 的**第一句**
`Git.is_dirty()` → `git2::Repository::open` 读 `.git/config` 被 macOS 拦在 `open()` 里
（未签名的 app 没有 `~/Documents` 的访问授权）：进程 0% CPU、state=S、永不返回。

它为什么必须先落：**它是一个只值一条 `warn!` 的检查，把任务挂死了四小时**，而那一轮超时还杀不掉它
（系统节点没有进程组）。完整叙事见决策 209 正文；这次实测同时是票 05 事件清单里
「调度器处置未生效」那一类的来源。

## 这次实测留下的三处实证（票面据此取材，不是推演）

1. **失败的那一轮什么都不留**：`支持rtk` 在 `architect-design` 失败于「校验错误：未找到结构化
   元数据」，`kanban_node_conversations` 里该任务 **0 行**——它是票 01 的实证。
2. **对讲台失败回合也什么都不留**：会话 `监测01M2QH0DHKGSGNVHC0WT2Q4CG0…` 里只有两条 `user` 行、
   零 token、零错误——用户**已经试过**「让值班长盯着这个任务」，它两次没回话且无从追查。
   它是票 04 的实证。
3. **项目级 run 是能跨重启存活的僵尸行**：`pseudo:project_analysis` 的 id 10/11/12 的
   `last_activity_at` 冻结在 11:11 / 11:15，`check_timeouts` 有意跳过它们，
   `requeue_running_tasks` 又不认它们（没有 `task_id`）。它是票 13 的实证。
