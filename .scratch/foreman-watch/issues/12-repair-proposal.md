# 12: 修复提议（复用提议表 + TTL 与指纹换义 + 前端钮）

**What to build:** 把「一次修复」做成一条**待你按的提议**，复用决策 207 已经造好的那张表。

复用 `kanban_foreman_proposals`（`session_id` / `summary` / `situation_json` / `claimed_at` /
`expires_at` / 四态 `status` / SSE 事件 / 前端确认钮 / 每小时过期清扫 / `claimed_at` 原子占用）
——它的每个字段都对得上修复这件事，新开一张表等于把 TTL、过期、占用、审计全部重写一遍。
**要加的是载荷里多一种「diff」形态**（现在只有 `tool` + `args_json`）。

**但那张表有两个为「当下这一刻」设计的性质，与「等你第二天早上看」直接冲突，必须改：**

1. **TTL 是 10 分钟**（`crates/core/src/storage/proposals.rs:22`）。修复类提议**不设 TTL**，
   只随年龄清理（与 `conversation_retention_days` 同口径 = 30 天）。不改的话，你早上看到的会是
   一排**灰按钮**，还得自己去合。
2. **`situation_fingerprint` 的拒执判据是为「改任务状态」设计的**（任务状态或 `allowed_actions`
   变了就别执行）。修复提议执行的是「合入一个分支」，分支不会因为别的事变迁而失效——
   **指纹的含义要换成「修复分支相对 base 是否还要 rebase、会不会冲突」**。

**实施收尾（2026-09-18）:**

- **迁移 0022 加了 `kind` 与 `payload_json`**（`api_call` 默认，向后兼容既有行）。
  为什么不让 `payload` 复用 `args_json`：那一份的语义是「工具的调用参数」，而修复**没有
  对应的工具端点**——执行分派按 `kind` 走 `repair` 那一支（`tool = "repair"` 只是分派的键，
  不是工具名）。
- **TTL 的落法**：`expires_at` 是 NOT NULL，故修复类用一个**远期值**
  （`FOREMAN_PROPOSAL_NO_TTL_DAYS` = 36500 天）。它表达的是「不按时间过期」，而不是一个
  算得出来的时刻；真正的生命周期归年龄清理（30 天口径）。用例正面钉住「八小时后仍可按键」，
  反面钉住「普通提议照旧 10 分钟过期」——两种过期语义在同一张表上并存，这正是票面要求
  写在明面上的那件事。
- **指纹换义**落在 `run_repair_proposal`：执行时先 `rebase_onto_with_auto_resolve`，
  冲突就拒执并列出文件（**不消耗提议**——照既有规矩，拒执只是「这一次不能执行」）。
  用例在 git 层正反两面都钉住：基准前进一步（不冲突）能合；基准改了同一段则冲突且报出文件。
- **按钮文案按形态分**：修复提议是「合入」（它会动主干），别的仍是「执行」。
- **`isRepairProposal` 的判据是 `kind` 而不是 `tool`**：`tool` 是分派键（将来可能改名），
  `kind` 是载荷形态的正式说法。
- **一处偏离票面（如实记）**：票面说「复用急停轮的 `.warn` 形态与 `PendingActions` 的渲染」。
  实际上提议轮**本来就**是既有的那种轮（`.prop` + 内联的 `pacts` 两颗钮），本票没有新开
  按钮面，也没有改它的形态；新增的只有修复那一块的 **闸门读数 + 可展开的 diff**。
- **两处没做**：
  1. **e2e 的那条用例没加**（`expectProposalReachable` 的并入）。既有的几何断言照旧覆盖
     提议轮本身，而修复那一块**追加**在参数位置的下面（diff 是折叠的，展开才占高），
     但「按 208 的视口量一遍修复提议」这件事**没有量过**——这是本票最实的一个缺口。
  2. **「过期」那一侧的回收没接**：过期清扫（每小时维护作业）会改状态，但它**不会**去删
     worktree——路径上少一个「清扫时顺带回收」的钩子。拒绝那一侧的回收已经接了。
     过期清扫属于 core 的维护作业，而回收需要项目路径（app 层的事），要么把回收做成
     可注入的钩子，要么让清扫只标状态、由下一次修复开始时顺带清理孤儿目录（后者更简单）。
  3. **「目标项目当场生效」那一路**（把补丁打进任务 worktree → resume → 任务带着它继续跑）
     **没有实现**：本票的执行只有「合入默认分支」一条。它在决策 210⑤ 的边界内
     （合入永远人按），但 §4.3 的「按诊断结论分派两份仓」还差这一半。

## 备注

**没有 TTL 的那条规则要写在明面上**：它让修复提议与别的提议行为不同。同一个界面上两种过期语义，
如果不写清，下次看到一条「过期」的提议会以为修复也一样——而修复恰好是**唯一一条你有意留给
自己第二天早上看的**。

## 闸门跑通后补记（2026-09-18）：**这条链在线上没有入口**

查 `start_repair` / `run_repair_gate` / `commit_repair` / `repair_diff` / `write_repair_diff` /
`propose_repair` 的调用者：**除了 `crates/core/tests/repair.rs`，一个都没有**。线上与修复有关的
代码只有**消费端**——`run_repair_proposal`（按下「合入」）与 `discard_repair_worktree`（拒绝 /
过期），而它们读的载荷只有 `propose_repair` 写得出来，后者又要有 `RepairOutcome`（= worktree +
闸门 + commit）。

于是一个环缺了口：**没有任何东西会去建那个修复 worktree**。票 11 的收尾写的是「那需要票 12 的
提议被按下」，而按下那条提议的前提恰恰是这条链已经跑完——环没闭上。

这一条**不是实现漏了一行**，是这批票面缺一格：值班长的工具清单里没有「开始一次修复」这个动作
（`FOREMAN_TOOL_SPECS` 19 项里没有它），所以它拿不到 worktree、也就没有合法的落点去 `write_file`。
而 `FOREMAN_PERSONA` 里已经写着「你也能**起草补丁**（改修复分支、过闸门、留下一个带标记的
commit）」——persona 承诺的能力没有对应的手。这正是 `FOREMAN_BASELINE` 上面那条注释警告的事
（「指示一个模型去调不存在的工具，正是它开始编造文件内容的起点」），也是决策 182 / 207 反复
踩过的那条线。

**没有擅自补这一格**：加一个工具就是动安全边界（`FOREMAN_TOOL_SPECS` 的注释原话），而
决策 209–212 没有裁过「修复怎么开始」。三种补法各有代价，需要一次裁决：

1. **`repair` 一族工具**（`action=start` 给 worktree / `action=finish` 跑闸门 → commit → 出 diff
   → 落提议）：模型驱动，最贴原设计；代价是多一个能改项目的动作要与 D 层、托管、确认钮各对齐一遍。
2. **人按的「修一下」钮**：在诊断包旁边加一颗按钮，点了就建 worktree 并把那一轮交回值班长；
   最窄，但「你说的自动修复」要多一次按键。
3. **只把 persona 那句删掉**（能力暂不承诺）：诚实，但本批 10–12 的工程量在线上等于零。

在此之前，票 10 / 11 / 12 的产物是**测试覆盖的库代码**，不是可用功能——这一条已同步到
本批 README 的收尾表里（状态由 `partial` 降为 `partial（链未闭环）`）。
