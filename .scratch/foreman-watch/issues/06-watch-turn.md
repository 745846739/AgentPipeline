# 06: 值守轮的运行机制 + 播报落进班次

**What to build:** 把待办表变成**一次真正的值班长回话**，并把结果播报进当前班次。

今天值班长只在 `POST /foreman/messages` 被调用时活一次（`ForemanRunner::say`，
`crates/core/src/pipeline/foreman.rs:787-977`）。值守轮复用它的全部机制（模型调用、工具循环、
token 记账、`briefing_json` / `traces_json` 审计），**区别只有一个：输入不是人打的话，
而是系统生成的简报**。

去抖：窗口（默认 60s）到期且有待办 → 唤醒一次；把窗口内所有待办合成一段简报喂进去。
窗口内没有新事件 → **不唤醒、不说话**（空闲时零 token）。

播报落点：**当前最新未归档班次**，沿用 `resolve_session(None)` 的既有语义
（`foreman.rs:984-1005`）。决策 204 的语义本来就是「一次值班 = 一个会话」——夜里值守长出来的
那一班，第二天早上打开就是它。

**代价如实记**：历史窗口是 24k 字符预算（`FOREMAN_HISTORY_BUDGET_CHARS`），一夜几十条播报会挤掉
对话上下文。所以票 05 的事件清单与票 07 的节流**不是可选项，是这个选择的前提**。

**实施收尾（2026-09-18）:**

- **共用走的是参数化入口**：`respond` 从「吃一句话」改成「吃 [`TurnInput`]」（`Human` /
  `WatchBrief`），`say` 与 `watch` 是它的两个外框。抄一份模型循环的代价是两处 token 记账 /
  痕迹 / 审计各自漂移，而那三样正是这一批要*建立*的可追溯性。
- **去抖从「最早那件」算**：窗口到期的那一趟把**所有**未消费且会唤醒的件一起喂进去
  （`render_watch_brief`），一条不丢；上限 50 条是粗兜底，超出的留表里下一轮再说。
  新增 `watch_debounce_sec`（默认 60），已同步 `docs/overview.md` §3。
- **消费只在成功之后**：模型报错 / 没回话时**不**置 `consumed_at`——一次网络抖动不该等于
  把这批事件丢了（有专门用例钉着）。
- **静默哨兵 `【无需处理】`**：模型只回这一行时，这一轮不落播报行、`watch()` 返回 `None`。
  敢让模型回哨兵是因为**判据偏向播报**：只有明确说了无需处理才静默，任何别的输出照常播报
  ——漏报一条真问题比多播一条贵得多。§2.4 的静默规则是为历史窗口预算设的，不是为省 token。
- **播报标记由后端加**（`【值守播报】`），不由模型自己说：它是「这一轮不是回话」这个事实的
  载体，前端按它把名牌渲染成「值班长 · 值守」，模型不该有机会说错。
- **驱动放在 app 层**（`Runtime::spawn_watch_loop`，10s 一趟）而不是 scheduler 的 tick 里：
  调度器不认识值班长，而「醒一次」要花模型的钱——挂在 tick 里会让每个调度器用例都变成一次
  潜在的 LLM 调用。
- **七条用例**：一次唤醒一条播报 + 消费 + 第二趟零调用；三件攒批（简报里三条都在、且标明
  来路）；窗口内不醒；无待办零 LLM 调用；静默不落行但消费；失败不消费；`slow_run` 不唤醒。
- **§12.3 加一行**：主动播报与回话两种轮的渲染判据（决策 199 约束着界面层行为）。

## 备注

**播报必须是「冷句」**：persona 已经定了「只报事实与建议、不寒暄、短句优先」
（`FOREMAN_PERSONA`）。主动播报是这套语气最该兑现的地方——半夜弹出一段带情绪的话，
会立刻变成「它有自己的看法」，而那是决策 182㉒ 明确挡掉的东西。
