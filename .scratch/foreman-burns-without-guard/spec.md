# 对讲台不再空转烧钱（foreman-burns-without-guard）

**Status:** done（12 张票全部落地，决策 302–311）

> **来源**：用户诉求「分析对讲台最近一次对话，为什么执行了这么久还没有解决问题」的**烧钱半边**。
> 实测底稿 = 对讲台会话 `01M3GFQR2JBRXAY61WY8AC9GJ5`（2026-09-27 03:50–06:17 UTC）：
> **95 轮顺序模型调用、2 小时 26 分、433,628 生成 token、23,850,987 prompt token、167 次工具调用、
> 0 条提议**，单次调用输入从 6,602 一路涨到 **561,210**（单调不降），收尾 `【已停】`。
> 经六轮拷问（Q1–Q22）逐项裁决定形。
>
> **显式修订一处既有口径**：**决策 293** —— 循环判据由**两条**扩到**三条**；
> 293 原有的 `REPEAT_LIMIT = 3` 与 `NO_PROGRESS_LIMIT = 5` 及其标定**不动**。
>
> **对决策 291 的推进（不构成冲突，291 本身无修订标记）**：291 明写「承认估算低估」但**不修估算**，
> 本 spec 修。
>
> **维持不动**：决策 292（人的那一轮**无硬界**，终点由人决定；值守轮 120k 硬界）、
> 决策 291 的「两端同源」容量算术与 80% 触发线的**用意**。
>
> **与另一条链的分工**：卡死侧（执行权 / 待办 / 授权）在 `.scratch/executor-never-returns/`，
> 两者之间**无阻塞边**。

## Problem Statement

我在对讲台说「协助任务 01M3BGVCX… 完成」，**2 小时 26 分、95 轮、43.4 万生成 token、2385 万
prompt token**，最后我按停——它回「它还没说出什么，没有部分结论可留」，**0 条提议**。

三层护栏在这 95 轮里**一次都没触发**：

- **成本界**：120,000 那条线只对**值守轮**是硬的；人的那一轮只落一句「过了值守轮那条预算线……继续还是停由你定」。433,628 烧完，没有别的反应。
- **窗口界**：轮内压缩的触发线 = 窗口的 80%，而配置的窗口是 128,000、真实单次输入却到了 561,210 照样成功——**全库没有一条「值班长轮内上下文超线」的日志**，管道侧的同款压缩却有命中，说明日志链路是通的，是这条线本身永远摸不到。
- **循环检测**：决策 293 专为「交替变着花样查」造的那条判据（连续 5 次读不到新东西）**0 次命中**。它看的是**结果字节指纹**——而这 95 轮里每次读数的字节都不同（日志偏移、`updated_at`、sqlite 行），于是永远「有新东西」。**它没接住它被造出来要接的那件事。**

更糟的是收场文案说「这一轮提的提议都还在，照样可以按」——**本会话 0 条提议**，它在说谎，
而唯一相关的那张提议（上一个会话 03:48:31 提的）已经在 04:29:51 过期作废。

## Solution

1. **窗口界的两个偏差必须同批校准**——配置的窗口值与 token 估算精度**一起**改。两者目前**偶然抵消**
   才让触发线压在真实窗口边缘；**只修一个比不修更糟**（论证见 Implementation Decisions 第 2 条）。
2. **给循环判据加第三条**：以**落库状态有没有变化**为进展（提议数 / 任务状态 / 游标），连续超线且
   毫无变化 → **提醒一次，不收口**。
3. **收场文案按实际提议数分支**：0 条就明说 0 条，别再说「提议都还在」。

## User Stories

1. As a 值班经理，I want 单次调用输入涨到真实窗口的 80% 时轮内自动压缩，so that 一轮不会无限膨胀。
2. As a 值班经理，I want 触发线用的是 provider **真实窗口**而不是一个过期的猜测，so that 那条线对应真实世界的边界。
3. As a 值班经理，I want token 估算对中文不再低估 5 倍以上，so that 触发线不会永远摸不到。
4. As a 值班经理，I want 这两处**必须同批生效**，so that 不会出现「只修一个反而更糟」。
5. As a 值班经理，I want provider 报上下文超长时窗口值**自动上调并落账**，so that 换模型或代理换实现后不用手工追。
6. As a 值班经理，I want 值班长长时间**没推动任何落库状态**时收到一次提醒，so that 「变着花样查」也能被认出来。
7. As a 值班经理，I want 这是**提醒不是收口**，so that 正当的深查不会被一刀切断。
8. As a 值班经理，I want 提醒与收口沿用决策 293 的两级动作与 `【未收口·在打转】` 标记族，so that 界面与心智模型不变。
9. As a 值班经理，I want 被按停时文案**按实际提议数**说话，so that 我不会去按一个不存在的提议。
10. As a 值班经理，I want 0 提议时明确告诉我「本轮没有提任何提议」，so that 我知道该做的是「再来一轮」而不是「去按键」。
11. As a 值班经理，I want 有提议时**保留**「提议都还在」的提醒，so that 决策 294 保留悬空提议的兑现点不丢。
12. As a 值班经理，I want 我问开放型问题（如「本机性能消耗情况」）时判据③ 也不会误伤，so that 只要真在推进就不会被打扰。
13. As a 值班经理，I want 人的那一轮**仍然没有硬预算**，so that 终点还是由我决定（决策 292 不动）。
14. As a 值班经理，I want 值守轮那条 120k 硬界照旧，so that 没人看着的时候它不会无限烧。
15. As a 维护者，I want 一条标定测试用这次 **95 条真实读数**断言「估算 ÷ 真读数」的比值，so that 估算精度有可回归的尺子。
16. As a 维护者，I want 一条回放测试用**真实调用序列 + 真实结果正文**把这轮重演一遍，so that 窗口界与判据③ 的触发有据可查。
17. As a 维护者，I want 回放 fixture **如实标注**哪些是真实数据、哪些是构造的，so that 测试的效力不被高估。
18. As a 维护者，I want 同一批改动**同时**跑对讲台与流水线两侧的压缩测试，so that 决策 291 的「两端同源」不被打破。
19. As a 维护者，I want 判据③ 的阈值按真实台账标定并**钉住常量**，so that 它不会被人随手调。
20. As a 维护者，I want 一条断言守住「0 提议时收场文案不含『提议都还在』」，so that 这句话的谎不会再出现第二次。
21. As a 维护者，I want 与决策 293 的关系是**显式修订**而不是悄悄改，so that 决策日志仍然可信。
22. As a 值班长，I want 收场时能查到「本轮实际提了几条提议」，so that 我不用靠记忆说话。

## Implementation Decisions

1. **窗口界同批校准两件**：
   - **窗口值**：先向代理确认真实窗口（已知**下限 ≥ 576,210** = 实测 561,210 + 输出预留），确认后写入
     provider 行；再加**撞墙自校准**——收到上下文超长错误时自动上调该行并落账（分类器 `is_context_window`
     已存在，决策 291(c) 的撞墙路本来就在用它）。
   - **估算精度**：`count_tokens` 由 `chars ÷ 4` 改为**加权启发式**——**CJK 字符按 1 token 计、其余仍 ÷ 4**。
     **零新依赖**（全仓当前没有任何 tokenizer 依赖；`vendor=openai` 但 model 经第三方代理，
     词表未必相同，引 `tiktoken` 可能把「已知偏低」换成「不可见的偏差」，后者更难查）。
     保留**单点实现**，守住决策 291 的「两端同源」。
2. **为什么必须同批（量化论证，写进票面）**：
   - 估算侧：第 94 轮真实输入 **561,210** 而压缩**没触发** ⇒ 当时估算 ≤ 102,400 ⇒ **低估 ≥ 5.5 倍**。
   - 窗口侧：配置 **128,000** 而 561,210 输入照样 `ok` ⇒ **至少低 4.5 倍**。
   - 两者**目前偶然抵消**：触发线 = 0.8 × 128,000 ≈ 102,400 估算 ≈ **56 万真实 token**，正好压在真实窗口边缘。
   - **只修窗口** → 线抬到约 0.8 × 真实窗口的**估算值** ≈ 数百万真实 token → **永不触发**。
   - **只修估算** → 线掉到 102,400 真实 token ≈ 真实窗口的 **18%** → **每轮都压、缓存全废**
     （决策 291 特意把线从 60% 抬到 80%，就是为了保住那份 94% 命中的 prefix 缓存）。
   - ⇒ **两个一起改，线才落在真实窗口的 80%。**
3. **判据③（显式修订决策 293）**：新增第三条——**进展 = 落库状态发生变化**（提议数 / 任务状态 /
   游标位置）；连续 N 次工具调用且三者全无变化 → **注入一次带标记的提醒**（提醒级，**不收口**）。
   N 按真实台账标定、**钉住常量、不做成可配**（照决策 293 / 224 / 256 的姿态）。
   **293 的两条原判据与 `REPEAT_LIMIT = 3` / `NO_PROGRESS_LIMIT = 5` 不动**——它们各自仍管着自己的形态。
   选「落库状态」而不是「调用来源指纹」的理由：这次「没进展」的事实**就是**「2.5 小时任务状态一字未动、
   0 条提议」，这个读数系统已经握着；而「读到没读过的东西」和「在推进」根本不是一回事——按来源指纹改，
   这次照样拦不住。
4. **收场文案按实际提议数分支**：0 条 → 「本轮没有提任何提议」+ 保留 `【已停】` 与操作台行；
   >0 条 → 现文案原样。**顺带排查同一收口路径是否还有别处默认「提议必然存在」**——这次只发现这一句，
   不代表只有这一句。
5. **回放 fixture 的诚实性**：`kanban_foreman_messages` 只存了工具名 + 参数摘要 + 成败，**没存结果正文**。
   ⇒ 回放用「**真实调用序列与参数** + 来自值班长上下文目录的真实结果正文（那批文件确实存在，
   189K / 187K / 186K…）；对不上的步**按真实长度构造**」。**这句必须原样写进测试注释与票面**，
   不许含糊——否则回放的效力会被高估。
6. **不动的三件**：人的那一轮无硬界（292）、值守轮 120k 硬界（292）、两端同源的容量算术与 80% 触发线的
   **用意**（291）——本 spec 修的是「这条线凭什么算得准」，不是「这条线该在哪」。

## Testing Decisions

**什么算好测试**：只测**外部行为**——压缩到底触发了没有（有没有那条日志 / 那个标记）、提醒注入了没有、
收场文案对不对、估算与真读数的比值落在哪个区间。不断言内部用什么算法算 token。

**接缝**：**不新增任何可测试性接缝**（照决策 299 / 300「§3.1 五条不动」，及决策 250 删假 seam）。
拟用全部为既有：

| 接缝 | 承担 |
|---|---|
| `AGENTPIPELINE_HOME`（每测试独占家目录） | 造 provider 行（窗口值、撞墙后的自动上调）、阈值行 |
| `Clock`（`start_paused` 手动推进） | 轮与轮之间的时序、判据③ 的阈值窗口 |
| LLM 响应流 `Script` 槽（决策 182 的 `Script::for_foreman()`） | 灌 95 步工具序列 / **0 提议停轮**（文案分支）/ **一次上下文超长错误**（撞墙自校准）/ 无进展序列（判据③） |

**标定集**：这次 **95 条真实读数**（`prompt_tokens` 6,602 → 561,210）直接做成 fixture，
断言 `估算 ÷ 真读数 ∈ [0.7, 1.5]`。**这条断言同时是「窗口界真的能触发」的前置证据**——
它不通过，触发线就还是摸不到。

**回放验收**：见 Implementation Decisions 第 5 条的诚实标注；断言的是三件外部行为——
**窗口界在第 N 轮触发**、**判据③ 在第 M 轮提醒**、**收场文案按实际提议数分支**。

**两侧同批**：`count_tokens` 被流水线 L3 压缩共用（决策 291「两端同源」），
⇒ 同一批改动必须**同时跑对讲台的轮内压缩测试与流水线的预算侧测试**，任一侧红都不算过。
prior art：决策 249 落地时给预算侧留下的那批单测（软限下 `Ok` / 软硬之间就地压缩 `Ok{compacted}` /
压缩后仍超硬 `Overflow` / `capacity = None` 恒 `Ok` / 锚不吞载入历史）。

**which modules**：token 估算、轮内压缩触发、provider 窗口读取与撞墙自校准、循环判据（纯函数）、
收场路径的文案生成、回放驱动。

**prior art**：`loops.rs` 的纯函数 + 阈值常量钉测试样式（判据③ 照抄这个形状）、
`foreman.rs` 集成用例（长轮与收场段）、`model_request` 预算侧单测（决策 249 那批）。

## Out of Scope

1. **收场时用 LLM 从 `traces` 综合出半截结论** —— 这次「95 轮无一字结论」是真问题，但它是**新能力**
   （要多花一次模型调用、要定义"半截结论"长什么样），与 `foreman-unbounded` 把只读子代理按
   Out of Scope 收掉（决策 296）同一姿态。
   **重开条件**：再出现一次「长轮无一字结论」，且人明确要求留下结论。
2. **阈值做成可配** —— 决策 293 已裁「没人会调的旋钮比没有更坏」，判据③ 沿用此裁。
3. **流水线节点的循环检测** —— `foreman-unbounded` spec §四 已记档（节点只有成功/失败两态，
   「先提醒再收口」在那里没有落点）。**重开条件**：流水线侧出现「节点反复重试且无进展」的实证。

## Further Notes

**残余风险（要如实写进票面）**：

1. **`context_window` 的真实值待票内确认**——已知下限 ≥ 576,210，但精确值要向代理核实；
   撞墙自校准是**兜底**不是替代（它要 provider 如实转达超长错误，代理不一定配合）。
2. **估算系数只在中英混合日志这一种内容上标定过**（本次 95 条）；换语种可能要复标——
   但即便复标失败，加权启发式也比 `chars ÷ 4` 的 5.5 倍偏差安全。
3. **判据③ 的阈值只有一本台账可标**（本次 95 轮）；照决策 293 的先例先钉一个留余量的常量，
   等有第二本台账再复标。

**与另一条链的关系**：`.scratch/executor-never-returns/`（卡死链）与本 spec **无阻塞边**，
可以并行。但要写清楚：**本次「查了 3 小时却无事可做」的第一因在卡死链**（任务根本动不了），
本 spec 的护栏救不了一个已经死锁的任务——所以两者都要做，顺序上卡死链优先。

**证据出处**（供票面复核）：95 条 `kanban_model_requests` 读数；全库 0 条「值班长轮内上下文超线」
而管道侧同款压缩有命中；`loops.rs` 的 `result_digest` 为字节哈希、任何新字节把 `stale` 归零；
收场文案所在位置与「0 条提议」的台账事实（该会话 `kanban_foreman_proposals` 计数为 0）。
