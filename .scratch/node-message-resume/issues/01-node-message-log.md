# 01: 节点内消息日志落库

**What to build:** agent 节点执行过程中，每一轮模型响应与每一个工具结果**逐条**落库，并且顺序保证
「assistant 响应先提交、再执行这一批工具」。进程被强杀后，日志里留下的是被杀前**已经完成**的全部消息——
这是后续所有恢复的素材。一条 run 的消息行合起来就是该 run 自包含的完整转录（含它起始时承接的前缀）。
日志记的是**原始转录**，压缩完全不碰它；会话表与它的截断行为一个字不改（观测面照旧）。

**Blocked by:** None（可立即开始）

**Status:** ready-for-agent

- [ ] 迁移（下一空号是 `0044`）建消息日志表：run 归属、任务、阶段、节点、agent_type、行内序号、角色、
      正文、工具调用的原始参数串、tool_call_id、工具名，以及「这条是合成回执」的标记位；
      索引按 (run, 序号) 与 (任务, 阶段, 节点)
- [ ] 一条 run 的消息行按行内序号能还原成消息数组，且内容与内存里那一份逐字段一致
      （工具调用的参数是原始 JSON 串，不做二次序列化）
- [ ] assistant 响应在**这一批工具的第一个执行之前**已经提交入库——测试用「让工具挂住」的替身，
      在挂住的那一刻断言库里已有那条 assistant 行。缺了这条顺序，崩溃会连模型刚说的话一起丢
- [ ] 每个工具结果返回后立即落行；工具失败也落行（内容是失败文本，与转录里的那份一致）
- [ ] 记的是原始转录：触发一次压缩（让内存里的消息数组被摘要改写）之后，断言日志行**仍含**
      被压掉的那些消息。日志只追加，不做任何改写与压缩事件记录
- [ ] 级联：删项目 / 删任务时新表随历史一起清，且**排在删 run 行之前**（外键是 NO ACTION，
      顺序错了会报 787）；删项目那条既有测试的表清单跟着加一行
- [ ] 保留期：进小时级维护的清理，与 `conversation_retention_days` 同一把尺子——不造第二把尺。
      **删除时点不得取「run 判终态」**（启动恢复第一件事就是把被 kill 的 run 标终态，
      那正是最需要日志的时刻）
- [ ] 观测面零变化：任务详情那三个会话路由与前端类型不动；会话表的截断行为照旧
- [ ] 决策日志追加一条，交代新表的语义（节点内 checkpoint）与它与会话表的分工
