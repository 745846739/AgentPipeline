# 值守轮失败的退避与留痕 — 落地依据

**状态：已裁（2026-09-25，决策 271）。** 本文是四张票的落地依据。

## 1. 起因：一次断供，37 行失败账（实测，不是推演）

2026-09-24 上午（CST）：

| 时刻 | 事实 | 证据 |
|---|---|---|
| 11:01:56 | 任务 `01M2VSNJ11W5VYPNFGY7FC6HXM` 被取消 → 待办 `952`（`task_cancelled`）落表 | `kanban_foreman_attention` |
| 11:03:09 → 11:06:17 | 值守轮**每 10 秒**醒一次、每次都失败，**20 行**：`HTTP 400 …insufficient credits`（本地代理 `commandcode-api-proxy` 余额不足） | `kanban_foreman_messages` 134–153 + 日志 `值守轮失败（待办未消费，下一趟重试）` |

| 次日 07:04:24 | 重启后第一趟：同一个没消费的待办 → 调用成功 → 播报并消费掉它 | 日志 `值守轮播报了一轮 session=01M34ST6Z3…` |

同一批的另外两处现场（一并修）：

- **名牌说错话**：失败账在时间线上顶着「发送失败」（`kind = "failed"` 的名牌），而那一批是**值守轮**
  在失败——值班经理一个字节都没发出去。判据只有 `kind` 一个字段，而它分不出「人的轮」与「值守的轮」。
- **播报标记被模型抄了一份**：重启后那条播报库里存的是
  `【值守播报】【值守播报】**无需你处置。**…`——模型从历史里学会这个前缀自己写了一遍，后端又加一遍；
  且因为回话不再以 `【无需处理】` 开头，那一轮当成播报发了出去（静默判据被自己的标记顶掉了）。

## 2. 今天的三条叠在一起，才是那台闹钟

1. **失败轮不消费待办**（票 06 的原话：一次网络抖动不该等于把这批事件丢了）——这条**对**，不动。
2. **值守轮每 10 秒一趟、没有退避**（`Runtime::spawn_watch_loop`，`WATCH_INTERVAL = 10s`）。
3. **失败不计入每小时唤醒上限**——那张账（`kanban_foreman_watch_wakes`）只在成功（`broadcast` /
   `silent`）与触顶（`capped`）时写；失败走 `record_failed_turn`，一次也没记过。
   **证据**：37 次失败发生在 `watch_max_wakes_per_hour = 12` 的配置下，上限一次都没响。

三条分开看都合理，合起来是「provider 一天不通 → 对讲台一天每 10 秒多一行」。附带代价：这些是
`system` 行，会被回灌进值班长的历史（映射成「操作台记的一轮」），长风暴还挤 24k 的历史预算。

## 3. 裁的四件事

### 3.1 分档退避（票 02）

失败后**下一次尝试**按类别推迟，成功一次即归零：

- **瞬时类**（网络、未知）：30s → 60s → 120s → 240s → 480s → **600s 封顶**。
- **等也不会好类**（`llm_auth` / `llm_model_not_found` / `llm_quota` / `llm_context_window` / `config`）：
  **300s → 600s → 1200s → 1800s 封顶**——余额不足按网络的节奏重试毫无意义，只会把噪声放大。
- 退避期内 `watch()` 直接 `Ok(None)`：**不问、不看不说话**（零模型调用、零落账）。
- 退避**只挡值守轮**：人说的话（`say`）不受影响，值班经理随时可以自己试一次。

取值不扩配置项（照决策 224「别在没有第二种诉求之前先扩契约」）：常量住在 `foreman.rs`，
与 `FOREMAN_MAX_ROUNDS` 同一姿态。

### 3.2 同批只落一行 + 恢复时一条汇总（票 03）

- 一批连续失败里，**同一类别只落第一行**（换类别才有下一行——「余额不足」与「连不上」是两件事，
  两个修法，不该合并）。首行自己说明这条规矩：`（此后同类失败不再逐条落账）`。
- **恢复**（退避之后第一次成功的那一轮）落一条 `system` 汇总：
  `【值守】已恢复：上一批连续失败 N 次（kind → kind），最后一次 <时刻>。`
- 判据**只在内存**（`ForemanRunner` 的一张状态表）：本轮不新造表、不加列——
  失败账的**账**仍是一行一行落库的，这里只是「同一批不重复落」。
  进程被杀则汇总不出现：首行仍在，读起来是「失败过一次」——比 37 行诚实，也不假装完整。

### 3.3 额度类失败独立成 `llm_quota`（票 01）

`HTTP 402`、以及 400 里认出额度 / 账单字样的错误体，归成 `LlmErrorKind::Quota`（`llm_quota`），
advice 直说「这不是网络问题，续费或换 provider」。

**来历**：那次代理回的是 `HTTP 400 …insufficient credits…`，`from_http` 认不出 → 落进
`Error::Llm` → 台账上的类别读作 `llm_network`，指引写「请检查 base_url 是否正确、网络是否可达」。
一次账单问题被读成配置问题，且按网络类的节奏重试——两条都是错的。

### 3.4 名牌与标记（票 04）

- 值守轮的失败账换一个前缀：`【值守没跑起来】`（前端与线上形态都不解析它，判据在字段上）。
- `message_wire` 的 `proactive` 派生扩一支：`system` 行 + 值守失败前缀 → `true`。
  **这就是决策 252③ 说的「将来要显示时不必再改线」**：两个正交字段的**字段集不动**，
  只是那一格终于有了真值（此前它恒为 `false`，因为派生把「自发的」写死在助理轮上）。
- 前端名牌：`failed && proactive` → 「值守 · 没跑起来」；`failed && !proactive` → 「发送失败」（原样）。
  判据抽成一个纯函数（`lib/talkTurns.ts::turnName`），组件只渲染（决策 199 / 252 的同一姿态）。
- 播报标记**只加一次**：后端在加 `【值守播报】` 之前先剥掉模型自己写的那一份，**静默判据在剥完之后判**
  ——于是「【值守播报】【无需处理】」这种回话仍然静默，且库里不再出现双前缀。

## 4. 明确不做

- **不改「失败不消费」**：那是这批里的地基（一次抖动 ≠ 丢事件），本批只加「多久之后再试」。
- **不把失败记进唤醒账**（`kanban_foreman_watch_wakes`）：那张表答的是「醒了几次 / 花了多少 token」，
  失败轮没醒也没花；把失败塞进去会让「这周值守花了多少」开始需要过滤条件。退避已经把频率压住了。
- **不给人轮的成功重置值守退避**：一次成功的人轮确实证明 provider 通了，但那要 `say` 去写 `watch` 的状态，
  收益只是「恢复早几分钟」。留一句话在这儿，有诉求再说。
- **不改 prompt**（不在简报里叮嘱模型「别自己写前缀」）：后端剥一遍就够了，prompt 效果回归属 v2 离线 eval。
- **不做「失败几次就转 pending 叫人」**：值守轮失败不是任务卡住，它是「这台机器叫不动」，
  由退避 + 一条汇总回答；再往上就是通知通道（决策 268）的事。
